# Known Limitations

This file records limitations that remain true in the sealed testing baseline. Resolved implementation gaps are intentionally not retained here.

1. **Advisory/read-only:** the publisher does not apply SQL warehouse configuration changes. HITL execution remains external.
2. **Realization ingestion:** the public JSON contract supports realization, but Phase 1 emits `NOT_APPLIED`; automated post-change measurement ingestion is not implemented. A future release must define the authoritative post-change measurement source, the attribution windows, the rollback semantics and the validation rules before realization becomes writable.
3. **Supported warehouse types:** active optimization is limited to `CLASSIC`, `PRO`, and standard `SERVERLESS`. Lakehouse Real-Time and unknown/future types fail closed at the supported-type gate.
4. **Historical AWS actual cost:** without CUR/effective-rate integration, customer AWS infrastructure actuals are not authoritative. Forward Pro/Classic AWS cost uses the versioned regional on-demand registry and is modeled.
5. **AWS pricing scope:** modeled AWS forward cost does not include organization-specific discounts, RI/Savings Plans, support, network, tax, or other charges unless explicitly represented in a future pricing source contract.
6. **Migration economics:** Serverless/Pro migration economics are pre-canary modeled ranges and require compatibility review plus canary validation.
7. **Photon:** Photon is an observed current-epoch billing state (`product_features.is_photon`), not a direct authoritative warehouse-config field. As of v2.7.1 it is **observation-only and left at its default**: no Photon recommendation is made. Databricks documents that Photon is enabled on SQL warehouses ([Photon docs](https://docs.databricks.com/aws/en/compute/photon)) but publishes no on/off price or DBU-rate change for SQL warehouses, and billing cannot show the runtime effect, so any estimate would be a guess. Whether a SQL warehouse can run with Photon off is not established by the public docs. Revisit only if real data shows a Photon-disabled warehouse and a measured canary effect.
8. **Compatibility evidence:** read-only compatibility API evidence is optional/non-authoritative; unavailable evidence falls back to HITL/unknown rather than guessed compatibility.
9. **Query-source attribution:** query source is multi-label where applicable; category percentages are not assumed to form a mutually exclusive distribution.
10. **Out-of-scope knobs:** query rewrite, storage optimization, scheduling optimization, Spot policy tuning, and statement-timeout tuning are outside the current active technique set.
11. **Workbook:** `workbook.xlsx` is a presentation projection only. Numeric annual-impact columns preserve signed economics; positive values are savings, negative values are cost increases, and unavailable values are not coerced to zero.
12. **Shared-warehouse segmentation:** size decisions are made per warehouse. One pathological query class (for example a single source or client application) can still dominate spill evidence on a shared warehouse once the sample and epoch-maturity gates pass; per-source segmentation is not implemented.
13. **Min-cluster utilization evidence:** the collector now gathers a task-time utilization measure (query task-minutes per running cluster-minute over the current epoch) as evidence on the size and min-cluster candidates, but no decision uses it yet and it is not calibrated on real data. Nothing proves a floor cluster is spare, so min-cluster reduction stays `TEST_REQUIRED` and its savings are modeled as an upper-bound range (`min_cluster_realization_*`). Post-canary measurement is what confirms realized savings.
14. **DBU price is list price (audit M6):** DBU dollars are observed usage multiplied by the published `system.billing.list_prices` rate, not the customer's invoiced or contract-effective price. Savings are modeled list-price savings; reconcile against invoices before financial reporting. An effective-rate registry is not implemented. Usage with no matching list-price row is not priced: it is reported as unpriced DBU and makes the affected actual or forward DBU cost unavailable (null) rather than understated.
15. **AWS cost is on-demand (audit M5):** Pro/Classic AWS cost uses on-demand EC2 list rates. The Warehouses API `spot_instance_policy` (default `COST_OPTIMIZED`) is neither read nor modeled, so actual AWS cost and the AWS part of savings can be materially lower. CUR or a Spot-mix source is required to fix this.
16. **Billing freshness (audit M7):** the forecast and "actual" window is the half-open interval `[today-365, last settled day covered by the billing watermark]`. A UTC day enters the cost basis only `billing_settle_hours` (24) after it ends and once its own workspace's billing watermark (newest SQL-product usage hour in the last 30 days, per workspace) has passed it. Databricks documents ORIGINAL billing records as typically available within 12 hours (longer for new workspaces) and gives no bound for RETRACTION/RESTATEMENT corrections, so a covered day can still be revised; the settle buffer narrows but does not remove that risk. The retracted DBU per originally billed DBU (it can exceed 1 when a day is corrected more than once) is reported as evidence on each package; it is a quality signal only and is not used in decisions or confidence yet. `--billing-ingested-through YYYY-MM-DD` pins every billing query to records ingested on or before that date, so a re-collection reproduces an earlier run despite later corrections. If a workspace has no SQL usage in 30 days its watermark is null and completeness is `UNVERIFIED`. `analysis_time` is captured before the queries run while the SQL uses `CURRENT_DATE()` at run time. The collector session is pinned to UTC and verified (it fails closed otherwise), so only a run that crosses UTC midnight can shift the SQL window by a day. Without a watermark (replay of older evidence) completeness is labeled `UNVERIFIED_ASSUMED_COMPLETE_THROUGH_PRIOR_DAY`. An epoch's first day is a partial day and is counted as a full day in the forecast basis.
17. **Max-cluster saturation is not temporally correlated (audit M3):** an increase needs queue pressure (30 days) and `time_at_max_pct >= 5%` (last 30 days of the resource window), but the two are not proven to coincide, and cluster-recycling transients are only excluded through the exact `cluster_count = max_clusters` match. Proving "queueing while at max" needs an interval join that is not collected.
18. **Auto-stop idle gaps vs RUNNING time (audit M1) and size calibration (audit M4)** are not addressed in the collector or estimators: idle gaps are not intersected with warehouse RUNNING intervals, and `_matched_epoch_factor` matches configuration but not workload. The AWS baseline, migration resource bounds and time at min/max/observed peak use the recent daily resource window (same calendar and 28/84-day blend as the DBU forecast; the capacity facts use its last 30 days); the auto-stop and min-cluster savings ratios still use whole-epoch idle and event totals (both terms over the same period) while query signals use 30 days. Design proposals with unexecuted draft SQL are in `docs/archive/audit-m-group-b.md`.
19. **Next step right after an applied change (M9):** Stage 1 (Reporter contract 1.2.0) publishes `recommended_plan.reevaluation` (the earliest time the 7-day epoch-maturity and cost-history gates clear, with their codes), `next_action = WAIT_FOR_REEVALUATION` when no step is ready, and `observed_change` (the observed config diff, unmeasured). It shows no next step or saving during that window. Stage 2 (a labeled, contingent carried-forward preview of the prior plan's remaining steps with rebased upside) is defined in the contract as a reserved, always-null `carried_forward_plan` and is not produced; it needs prior-epoch evidence (M2) and an approved exception to "historical epochs are calibration only". `earliest_reevaluation_time` ignores billing ingestion lag and query-sample gates. `observed_change` can describe an old change; read `changed_at`.
20. **Unexecuted SQL:** none of the collector SQL, including the per-workspace billing watermark query, the ingestion-date cutoff predicates, the daily resource series query and the list-price join, has been run against a real warehouse.
21. **Warehouse configuration retention:** the retention of `system.compute.warehouses` has not been verified on a live account. A warehouse whose only configuration snapshot ages out of the table would not be discovered.
22. **Configuration epoch edge cases:** snapshots that share a `change_time` are collapsed to one deterministic row, so if they differ only in tags the tags kept are arbitrary (tags cannot be used as a sort key). A restored (undeleted) warehouse with an unchanged configuration continues its earlier epoch, so the deleted interval counts as zero-usage days in its cost history. Snapshots written for properties that are not table columns (if any exist) do not start a new epoch. None of these has been observed on a live account.
23. **Billing completeness with a single or fully idle account:** when a workspace's billing watermark stalls because its warehouses stopped running, the account-wide watermark from another, active workspace releases the idle $0 days. In a single-workspace account, or when every workspace is idle, there is no fresher watermark, so those idle days stay excluded from the forecast basis as possibly incomplete.
24. **Billing completeness on the watermark's own day:** the daily resource series cannot place running minutes within a day, so running on the day of a workspace's billing watermark counts as ingestion lag only when it provably follows the watermark (more running minutes than had elapsed before it). A short run just after the watermark while ingestion is stalled can therefore leave that day counted as complete with part of its billing.
25. **Business-hours patterns:** the aggregate collector contract does not carry enough time-of-day detail to prove business-hours usage patterns, so no decision relies on them.
26. **Scenario policy:** the Phase-1 recommended scenario is always current-type optimization (Plan A). Warehouse-type migration is evaluated as an alternative experiment and is never auto-selected.
27. **Threshold calibration:** thresholds are conservative policy defaults and are not calibrated on live data. They change only through versioned policy changes backed by golden and regression evidence (`thresholds.md`).
