# Known Limitations

This file records limitations that remain true in the current release. Resolved implementation gaps are intentionally not retained here.

1. **Advisory/read-only:** the publisher does not apply SQL warehouse configuration changes. HITL execution remains external.
2. **Realization ingestion:** the public JSON contract supports realization, but Phase 1 emits `NOT_APPLIED`; automated post-change measurement ingestion is not implemented. A future release must define the authoritative post-change measurement source, the attribution windows, the rollback semantics and the validation rules before realization becomes writable.
3. **Supported warehouse types:** active optimization is limited to `CLASSIC`, `PRO`, and standard `SERVERLESS`. Lakehouse Real-Time and unknown/future types fail closed at the supported-type gate.
4. **Historical AWS actual cost:** without CUR/effective-rate integration, customer AWS infrastructure actuals are not authoritative. Forward Pro/Classic AWS cost uses the versioned regional on-demand registry and is modeled.
5. **AWS pricing scope:** modeled AWS forward cost does not include support, network, tax, or other charges unless explicitly represented in a future pricing source contract. Discounts, RI/Savings Plans and Spot are limitation 15.
6. **Migration economics:** Serverless/Pro migration economics are pre-canary modeled ranges and require compatibility review plus canary validation. They are priced relative to billing: the same model applied to the current warehouse must reproduce its billed DBU forecast within the reconciliation band, or the estimate is withheld. The target runs at its own cost-minimizing auto-stop on the measured idle gaps, so its running time carries the same restart-cost assumption (limitation 18). A migration whose best case still costs more than today is held (`MIGRATION_NOT_COST_EFFECTIVE`). The AWS target cost stays modeled.
7. **Photon:** Photon is an observed current-epoch billing state (`product_features.is_photon`), not a direct authoritative warehouse-config field. It is **observation-only and left at its default**: no Photon recommendation is made. Databricks documents that Photon is enabled on SQL warehouses ([Photon docs](https://docs.databricks.com/aws/en/compute/photon)) but publishes no on/off price or DBU-rate change for SQL warehouses, and billing cannot show the runtime effect, so any estimate would be a guess. Whether a SQL warehouse can run with Photon off is not established by the public docs. Revisit only if real data shows a Photon-disabled warehouse and a measured canary effect.
8. **Compatibility evidence:** read-only compatibility API evidence is optional/non-authoritative; unavailable evidence falls back to HITL/unknown rather than guessed compatibility.
9. **Query-source attribution:** query source is multi-label where applicable; category percentages are not assumed to form a mutually exclusive distribution.
10. **Out-of-scope knobs:** query rewrite, storage optimization, scheduling optimization, Spot policy tuning, and statement-timeout tuning are outside the current active technique set.
11. **Workbook:** `workbook.xlsx` is a presentation projection only. Numeric annual-impact columns preserve signed economics; positive values are savings, negative values are cost increases, and unavailable values are not coerced to zero.
12. **Shared-warehouse segmentation:** size decisions are made per warehouse. Spill concentrated in a few statement sources is detected and holds an upsize (a rewrite is the fix), but other signals are pooled: one pathological query class (for example a single source or client application) can still dominate latency or queueing evidence on a shared warehouse once the sample and readiness gates pass; per-source segmentation of those signals is not implemented.
13. **Min-cluster utilization evidence:** the collector now gathers a task-time utilization measure (query task-minutes per running cluster-minute over the current epoch) as evidence on the size and min-cluster candidates, but no decision uses it yet and it is not calibrated on real data. Nothing proves a floor cluster is spare, so min-cluster reduction stays `TEST_REQUIRED` and its savings are modeled as an upper-bound range (`min_cluster_realization_*`). Post-canary measurement is what confirms realized savings.
14. **DBU price is list price:** DBU dollars are observed usage multiplied by the published `system.billing.list_prices` rate, not the customer's invoiced or contract-effective price. Savings are modeled list-price savings; reconcile against invoices before financial reporting. The package forecast assumptions and the workbook notes state this basis next to every figure. An effective-rate registry is not implemented. Usage with no matching list-price row is not priced: it is reported as unpriced DBU and makes the affected actual or forward DBU cost unavailable (null) rather than understated.
15. **AWS cost is on-demand:** Pro/Classic AWS cost uses on-demand EC2 list rates. The Warehouses API `spot_instance_policy` (default `COST_OPTIMIZED`) is neither read nor modeled, so actual AWS cost and the AWS part of savings can be materially lower. CUR or a Spot-mix source is required to fix this.
16. **Billing freshness:** the forecast and "actual" window is the half-open interval `[today-365, last settled day covered by the billing watermark]`. A UTC day enters the cost basis only `billing_settle_hours` after it ends and once its own workspace's billing watermark (newest SQL-product usage hour in the last 30 days, per workspace) has passed it. Databricks documents ORIGINAL billing records as typically available within 12 hours (longer for new workspaces) and gives no bound for RETRACTION/RESTATEMENT corrections, so a covered day can still be revised; the settle buffer narrows but does not remove that risk. The retracted DBU per originally billed DBU (it can exceed 1 when a day is corrected more than once) is reported as evidence on each package; it is a quality signal only and is not used in decisions or confidence yet. `--billing-ingested-through YYYY-MM-DD` pins every billing query to records ingested on or before that date, so a re-collection reproduces an earlier run despite later corrections. If a workspace has no SQL usage in 30 days its watermark is null and completeness is `UNVERIFIED`. `analysis_time` is captured before the queries run while the SQL uses `CURRENT_DATE()` at run time. The collector session is pinned to UTC and verified (it fails closed otherwise), so only a run that crosses UTC midnight can shift the SQL window by a day. Without a watermark (replay of older evidence) completeness is labeled `UNVERIFIED_ASSUMED_COMPLETE_THROUGH_PRIOR_DAY`. An epoch's first day is a partial day and is counted as a full day in the forecast basis.
17. **Max-cluster saturation is not temporally correlated:** an increase needs queue pressure (30 days) and `time_at_max_pct` at or above `time_at_max_pct_saturated` (last 30 days of the resource window), but the two are not proven to coincide, and cluster-recycling transients are only excluded through the exact `cluster_count = max_clusters` match. Proving "queueing while at max" needs an interval join that is not collected.
18. **Auto-stop restart cost is an assumption:** an auto-stop value is priced on idle gaps intersected with observed running time, net of the restarts it adds. A Pro/Classic restart costs the documented start time (about 4 minutes) per floor cluster, which assumes starting minutes are billed; Databricks does not document it, so a raise (whose saving is only restarts avoided) is always a canary that measures billed cost. A Serverless restart (documented 2 to 6 seconds, priced at the upper end) costs about nothing. The cold-start budget bounds the share of queries that meet an added restart, including cache warm-up, but does not measure their latency. The AWS baseline, migration resource bounds and time at min/max/observed peak use the recent daily resource window (same calendar and 28/84-day blend as the DBU forecast; the capacity facts use its last 30 days); the min-cluster savings ratio still uses whole-epoch event totals while query signals use 30 days. Design proposals with unexecuted draft SQL are in `docs/archive/audit-m-group-b.md`.
19. **Next step right after an applied change:** Stage 1 publishes `recommended_plan.reevaluation` (the earliest time the readiness (`readiness_min_billed_days` settled billed days in the current epoch) and cost-history (`min_economics_cost_history_days`) gates clear, with their codes), `next_action = WAIT_FOR_REEVALUATION` when no step is ready, and `observed_change` (the observed config diff, unmeasured). It shows no next step or saving during that window. Stage 2 (a labeled, contingent carried-forward preview of the prior plan's remaining steps with rebased upside) is defined in the contract as a reserved, always-null `carried_forward_plan` and is not produced; it needs prior-epoch evidence and an approved extension of the older-epoch rule, which today only lets an older epoch hold a capacity cut, carry evidence a change cannot affect and restore its value in a canary rollback. `earliest_reevaluation_time` is the next settled day for the readiness gate and ignores billing ingestion lag, days without billing and query-sample gates, so a run on that day can still find the configuration not ready. `observed_change` can describe an old change; read `changed_at`.
20. **Unexecuted SQL:** none of the collector SQL, including the per-workspace billing watermark query, the ingestion-date cutoff predicates, the daily resource series query, the retained-event restriction on the idle-gap sample, the busy-minutes union of query intervals, the running-idle queries (idle gaps intersected with running segments), the per-minute concurrency query, the spill-by-statement-source query, the carried-evidence queries, the canary guard query, the weekly query counts behind the growth guard, the billed node type and SQL tier columns and the list-price join, has been run against a real warehouse.
21. **Warehouse configuration retention:** Databricks documents a 365-day retention for `system.compute.warehouses` and a new row only when a warehouse's configuration changes, but not whether an unchanged warehouse's only row survives that period. A warehouse whose only snapshot ages out cannot be analyzed; a live run lists every SQL warehouse billed in the last 30 days and active in its region without a snapshot (warning in `publisher.log`, `unseen_billed_warehouses` in `manifest.json`) instead of missing it silently.
22. **Configuration epoch edge cases:** snapshots that share a `change_time` are collapsed to one deterministic row, so if they differ only in tags the tags kept are arbitrary (tags cannot be used as a sort key). A restored (undeleted) warehouse with an unchanged configuration continues its earlier epoch, so the deleted interval counts as zero-usage days in its cost history. Snapshots written for properties that are not table columns (if any exist) do not start a new epoch. None of these has been observed on a live account.
23. **Billing completeness with a single or fully idle account:** when a workspace's billing watermark stalls because its warehouses stopped running, the account-wide watermark from another, active workspace releases the idle $0 days. In a single-workspace account, or when every workspace is idle, there is no fresher watermark, so those idle days stay excluded from the forecast basis as possibly incomplete.
24. **Billing completeness on the watermark's own day:** the daily resource series cannot place running minutes within a day, so running on the day of a workspace's billing watermark counts as ingestion lag only when it provably follows the watermark (more running minutes than had elapsed before it). A short run just after the watermark while ingestion is stalled can therefore leave that day counted as complete with part of its billing.
25. **Business-hours patterns:** the aggregate collector contract does not carry enough time-of-day detail to prove business-hours usage patterns, so no decision relies on them.
26. **Scenario policy:** the Phase-1 recommended scenario is always current-type optimization (Plan A). Warehouse-type migration is evaluated as an alternative experiment and is never auto-selected.
27. **Threshold calibration:** thresholds are conservative policy defaults and are not calibrated on live data. They change only through versioned policy changes backed by golden and regression evidence (`thresholds.md`).
28. **Always-on warehouse with no retained event:** `system.compute.warehouse_events` keeps 365 days. A warehouse that was never restarted in that period (an always-on warehouse) has no retained event, so its running time is unknown: the AWS baseline, capacity facts (time at min/max, observed peak) and auto-stop savings are unavailable and fail closed until it restarts and an event is retained. A billing-hours fallback (estimating running time from billed DBU) is not implemented.
29. **Metadata statements are not excluded from latency:** the decision population excludes result-cache queries only (failed and cancelled queries stay in, because a statement timeout is latency) and does not exclude metadata statements (`SHOW`, `DESCRIBE`, `USE` and similar), because the `statement_type` values are not documented. Excluding them needs a real sample of `system.query.history`.
30. **Unpriced size canaries:** a Pro/Classic size change is priced only from the workspace's billed DBU per cluster-hour for both sizes. A change to a size that has never run in the workspace has no observed rate, so it is not priced: it stays a canary with null economics.
31. **Max-cluster increase best case:** the best case of a max-cluster increase is no added cost (factor 1.0): the same queries run on more clusters at once, so total running time does not grow. Added clusters that start and idle without shortening the work would cost more than that; the base case is what peak demand needs under the new ceiling (Pro/Classic with concurrency evidence) and the worst case runs every added cluster whenever the warehouse sat at its ceiling ([LLD §17.6](../architecture/lld.md)).
32. **Kept-alive detection:** running time past the current auto-stop with no query running is reported (`kept_alive_flag_pct`) and never priced as removable, but its cause (open sessions, result fetching, a keep-alive client) cannot be told apart from the system tables, and a tiny-query polling pattern is flagged from query counts and client applications only. A human has to find what holds the warehouse up.
33. **Older-epoch concurrency is configuration-dependent:** an earlier configuration's peak query concurrency depends on its size and cluster limits (a smaller size shows more concurrency for the same work), so it is used only to hold a capacity cut, never to choose a target or an economic figure. The hold lasts until the older epoch ages past 365 days, so capacity can stay after the team that needed it leaves; the blocker stays visible for a human override.
34. **Infrequent workloads:** a workload that runs less often than weekly is forecast over whole billing cycles (`forecast_min_cycles`), which needs at least that many cycles in the current epoch's billing history. A quarterly workload therefore needs an epoch about a year old, and semi-yearly and yearly workloads (fewer than three runs in 365 days), like a single billed day, stay unknown (null forward cost, no savings estimate). A close longer than a week (six or more business days a month) is not a periodic burst and uses the run-rate model, which can be off by up to about 40% depending on where its windows fall. Whole cycles are not whole calendar periods for a cadence with two runs a month (for example the 1st and 5th): in an epoch of about three months its forecast can be off by about 30% until more cycles accrue, and a historic pause in a short history keeps a stopped job counted as current for up to about one long cycle.
35. **Carried evidence crosses only changes that cannot affect it:** demand and per-query evidence carries across auto-stop, max- and min-cluster changes and capacity queueing across auto-stop changes, inside the last 30 days and only while the current epoch is younger than 30 days (the map: LLD 10.2); nothing carries across a size, type or channel change, weekly counts never carry, and running time, idle time, cluster-minutes and billing never carry. A boundary minute is split between the two epochs in the epoch collectors, while the carried concurrency merges the minutes of the period, so the two can differ by that minute.
36. **Canary guard window and economics:** the canary guard runs only while the change is at most 30 days old and compares the epoch since the change with the previous epoch's last 30 days. It does not see seasonal differences between the two windows, so a seasonal swing can trip or hide a guard. A rollback's economics are not priced: the restored configuration's cost is not estimated. With demand evidence carried but not capacity queueing (after a min- or max-cluster change), a decision reads its query sample over the demand period and its queueing over the current epoch alone. The guard compares with the immediately preceding epoch only: if another change is applied before a pending rollback (out of plan order), the next run no longer sees the canary-type change.
