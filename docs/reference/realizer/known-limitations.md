# Realizer Known Limitations

This file records limitations that remain true in the current Realizer release (component version 1.4.0). Resolved implementation gaps are intentionally not retained here. The Publisher's own limitations are in [`../publisher/known-limitations.md`](../publisher/known-limitations.md).

## Not yet possible

1. **Input contract:** the Realizer reads exactly the Reporter JSON Contract the current Publisher writes ([`contracts/shared/reporter-json-contract.md`](../../contracts/shared/reporter-json-contract.md)); `validate_package` in `src/realizer/config/loader.py` refuses any other `contract_version`, a package that fails the committed schema or whose id and full hash do not match its content, a `realization` block other than the Publisher's empty placeholder, and a carried-forward plan. A package from an older or newer Publisher contract cannot be realized until the Realizer is changed for it.
2. **Live measurement of auto-stop only:** a live run (`--profile`, [`source-evidence-contract.md`](../../contracts/realizer/source-evidence-contract.md) section 18) measures a changed auto-stop with a replay counterfactual. A change to size, cluster counts or warehouse type is observed (application, conformance, independent changes, the guards before and after it and its billed change at the pre-change query mix) but has no counterfactual yet, so it carries no realized economics; a performance fix or a zero-priced capacity cut is still judged on those guards ([`policy-contract.md`](../../contracts/realizer/policy-contract.md) section 7).
3. **No live run on a connected workspace yet:** the live measurement and the backtest (`--backtest`, [`source-evidence-contract.md`](../../contracts/realizer/source-evidence-contract.md) section 19) run in tests and in `--demo` on simulated worlds through the Publisher's collector SQL (`publisher.analyzer.collector.demo.simulate_demo_world`); neither has been run against a connected Databricks workspace, so no real system-table result has been compared with them. The simulator bills running time only, not the restart cost the replay assumes, so a simulated change whose saving rests on avoided restarts (the backtest demo's raised auto-stop) shows the billed cross-check disagreeing; only real billing can say which is right.
4. **Realization levels are not implemented:** the step, plan and package realization levels ([`repo-reorg-design.md`](../../architecture/realizer/repo-reorg-design.md) section 10) do not exist. The measurement per application episode (candidate or scenario scope) is the closest thing; inventing the levels would be new behavior.
5. **Reviewer checks are not implemented:** the reviewer checks of design section 11 (evidence completeness, lifecycle, baseline, attribution, overlap, no double count, annualization, consistency) are not implemented as checks that can reject. The Reviewer assembles what the single-file release decided.
6. **The last days before a rollback or a drift are not measured:** a live run measures whole settled weeks of the configuration in force, so once a rollback or a drift has closed an episode, the days between its last measurement and the closing change are never measured; the savings to date cover the measured days only and say how many days they cover ([`ledger-contract.md`](../../contracts/realizer/ledger-contract.md) section 15). Runs more than twelve weeks apart leave uncovered days the same way.

## Original behavior kept for parity

The Realizer was extracted from the single-file release with identical outputs, and the behaviors below were found on the way and deliberately not changed, because a fix alters stored outputs and decisions. Each is a candidate for a separately reviewed change that regenerates the stored scenarios. The detail of each, with the phase that found it, is in [`repo-reorg-parity.md`](../../proposals/realizer/repo-reorg-parity.md); the gap review ([`gap-review.md`](../../proposals/realizer/gap-review.md)) schedules each.

7. **Redundant readiness evaluation:** on the realize path `calculate_economics` re-evaluates readiness, which is always ready there. Nothing observable changes.
8. **Cost increase reads as under-realized:** on a savings step, a realization that is a cost increase is classified as under-realized with re-optimization recommended and a negative ratio, and a claimable one is attributed as negative savings. (A performance fix or a capacity cut is not a savings step: its cost change is reported, never classified or claimed.)
