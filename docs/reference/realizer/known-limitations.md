# Realizer Known Limitations

This file records limitations that remain true in the current Realizer release (component version 1.0.0). Resolved implementation gaps are intentionally not retained here. The Publisher's own limitations are in [`../publisher/known-limitations.md`](../publisher/known-limitations.md).

## Not yet possible

1. **Input contract:** the Realizer reads exactly the Reporter JSON Contract the current Publisher writes ([`contracts/shared/reporter-json-contract.md`](../../contracts/shared/reporter-json-contract.md)); `validate_package` in `src/realizer/config/loader.py` refuses any other `contract_version`, a package that fails the committed schema or whose id and full hash do not match its content, a `realization` block other than the Publisher's empty placeholder, and a carried-forward plan. A package from an older or newer Publisher contract cannot be realized until the Realizer is changed for it.
2. **No live collector:** the engine takes a normalized post-change observation ([`source-evidence-contract.md`](../../contracts/realizer/source-evidence-contract.md)), replayed from a file (`--observation`) or generated as the synthetic demo (`--demo`, `--demo-modified`). `collector.py` holds only `load_observation` and `demo_observation`; nothing reads a system table or an API.
3. **No live source-system end-to-end run:** the Realizer has never been run against a connected Databricks workspace, and there is no integration test of collector SQL, source schema or a full run against configured source systems. A real run needs limitation 2 resolved first.
4. **No `.xlsx` workbook writer:** the single-file release rendered a Realizer workbook extension with the `artifact_tool` runtime and the retired Workbook v1.1.0 reporter, and that renderer is not part of this repository. The workbook projection (the rows a renderer would draw, [`workbook-compatibility-contract.md`](../../contracts/realizer/workbook-compatibility-contract.md)) remains in `src/realizer/contracts/report.py`.
5. **Realization levels are not implemented:** the step, plan and package realization levels ([`repo-reorg-design.md`](../../architecture/realizer/repo-reorg-design.md) section 10) do not exist. The measurement per application episode (candidate or scenario scope) is the closest thing; inventing the levels would be new behavior.
6. **Reviewer checks are not implemented:** the reviewer checks of design section 11 (evidence completeness, lifecycle, baseline, attribution, overlap, no double count, annualization, consistency) are not implemented as checks that can reject. The Reviewer assembles what the single-file release decided.

## Original behavior kept for parity

The Realizer was extracted from the single-file release with identical outputs, and the behaviors below were found on the way and deliberately not changed, because a fix alters stored outputs and decisions. Each is a candidate for a separately reviewed change that regenerates the stored scenarios. The detail of each, with the phase that found it, is in [`repo-reorg-parity.md`](../../proposals/realizer/repo-reorg-parity.md); the gap review ([`gap-review.md`](../../proposals/realizer/gap-review.md)) schedules each.

7. **Billing restatement reprocessed:** reprocessing a billing-restatement observation once more appends a second `BILLING_CORRECTION_RECORDED` entry whose `corrects_entry_id` is the restated measurement itself, and the snapshot's `correction_count` goes from 1 to 2; a further pass adds nothing. Every other scenario is idempotent on its last observation. The `restatement-reprocessed` scenario pins the current behavior.
8. **Counterfactual id hashes the raw window start:** the counterfactual id hashes the observation's `window_start_utc` as given, while the validation and measurement ids fall back to the applied time when it is null. An observation without a window (one without economics) therefore hashes a null there, not the applied time.
9. **Redundant readiness evaluation:** on the realize path `calculate_economics` re-evaluates readiness, which is always ready there. Nothing observable changes.
10. **Cost increase reads as under-realized:** a cost increase is classified as under-realized with re-optimization recommended and a negative ratio, and a claimable one is attributed as negative savings.
11. **Duplicate entries still rewrite files:** a repeated entry is suppressed by id on each append, so a run that records an event an earlier run (or an earlier slot) already recorded logs `ledger.duplicate_suppressed` and still rewrites its evidence and regeneration files with the same content.
