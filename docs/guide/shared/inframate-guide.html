How the warehouse optimizer thinks

The Publisher reads system tables and writes one locked RecommendationPackage per SQL warehouse. The Realizer takes one package after an owner applies a change and records what was actually saved. This guide walks both, layer by layer, with one real warehouse as the running example.

01Foundations

The product in one picture

inframate-v1 is two read-only products around one hand-off file. The Publisher reads Databricks system tables and writes one locked RecommendationPackage per SQL warehouse, saying which configuration change would save money and how sure it is. A person reviews the package and applies a change by hand. The Realizer then takes that package, watches the warehouse after the change and records in an append-only ledger what was actually saved.

Two products, one contract

Publisher 2.14.0

Answers "what should change on this warehouse, why, and what is it worth?" Entry point publish. Writes one package per warehouse under packages/, plus evidence.json, workbook.xlsx and manifest.json.

Realizer 1.8.0

Answers "the owner applied it; what did it actually save, and can we claim it?" Entry point realize_request. One PKG in, one RPKG and one ledger out.

The hand-off is the Reporter JSON Contract 3.1.0. The Realizer accepts exactly the contract version it was built for (3.1.0), checks the package against the Publisher's schema and recomputes its PKG- ID before it reads anything else. Chapter The RecommendationPackage explains the file field by field.

Invariants that shape every layer

These rules come from the product requirements and the domain model. When a design question comes up, they usually settle it.

Deterministic

Identical normalized evidence, cost profile and versions produce identical decisions, IDs, confidence and economics, byte for byte. Nothing reads the wall clock or randomness during a decision; the analysis time is an input. See determinism.

Read-only

OAuth profiles only; a static personal access token is rejected. There is no mutation API and no apply step. The only HTTP verb in the shared access layer is GET (api_get). See human in the loop (HITL).

Fail closed on warehouse types

Only CLASSIC, PRO, SERVERLESS are analyzed. An unknown or future type is excluded with a reason code, never routed into an existing algorithm (_is_supported_warehouse). See fail closed.

Unknown is null, never zero

Unpriced usage, missing AWS prices or thin history leave a cost null with a status code. A zero would read as "free" and inflate savings. DBU and AWS costs always stay separate components.

One candidate per knob

Every package decides each active knob exactly once: warehouse_size, max_clusters, min_clusters, auto_stop_minutes, warehouse_type. Photon and the warehouse channel are observed and reported, never recommended, because neither has a priced effect.

The JSON is the truth

The package is the machine source of truth. The workbook (Executive Summary, Warehouse Portfolio, Scenario Plans, Recommendation Registry) only projects it: no formula, estimate, ID or selection logic lives in Excel.

Check yourself
Who changes the warehouse configuration?

A person. Both products are read-only: no mutation API, no apply step. The Publisher proposes, the owner applies by hand, the Realizer observes the result in system tables.

A billing row has no list price. What cost does the package show?

null with an unavailability status, never 0. A zero would make the usage look free and overstate savings; unknown stays visible as unknown.

Why does the Realizer recompute the package ID before reading the package?

The ID is a content hash. Recomputing it proves the file is exactly what the Publisher produced, so the Realizer measures against the real recommendation and not an edited copy.

Photon is enabled on a warehouse. Will the Publisher recommend turning it off?

No. Photon is inferred from billing and reported in current_config.photon, but Databricks publishes no Photon on/off price for SQL warehouses, so any savings figure would be a guess.

02Publisher

Publisher pipeline

A Publisher run is seven capabilities called once each, in a fixed order, by a facade that holds no domain logic. Each capability answers one question and hands an immutable result to the next: the Analyzer observes, the Governor decides what may be considered, the Optimizer decides and prices isolated changes, the Packager plans and prices scenarios and assembles the package, the Reviewer verifies twice, and the Reporter writes files.

The facade and the context

publish only sequences calls. It first calls build_context, which validates the execution mode, parses the --cost-profile flags and resolves the run scope through the config layer (resolve_scope), so a bad flag is refused before any evidence is read. A live run then calls preflight, which logs an early warning when --source-region is not in the AWS price registry, so the mistake shows before the long collection instead of after it. The result of build_context is a RunContext holding the request, a fresh Thresholds and the scope.

A live collection reads 365 days of system tables, so the Analyzer saves evidence.json right after extraction, before any decision. If a later stage refuses the run or crashes, publish appends the saved path and the --from-evidence command to the error (evidence_saved_note), so the expensive part is never lost.

Two in-memory entry points run the same capabilities on evidence already in hand and write nothing: evaluate_warehouses stops after the scenario gate, build_recommendation_packages returns reviewed packages. Tests and the golden harness use them.

What each capability decides, and what it never decides

Analyzer

run collects evidence (demo, replay or live), then analyze computes findings per knob for every supported warehouse under its cost profile. Unsupported types keep their evidence but get no findings. A live run persists the evidence as soon as it is extracted.

Never decides eligibility, a recommendation or economics.

Governor

govern narrows the fleet to the run scope's warehouses, records a fail-closed exclusion for each unsupported one and passes the scope on. A live run also stops here when the source region has no AWS price, unless the request allows publishing with AWS cost unavailable; the early warning from preflight announces that before collection.

Never observes and never recommends.

Optimizer

Optimizer runs the five techniques in a fixed order, then the canary rollback; in_scope drops out-of-scope decisions afterwards (a rollback always stays), and the candidate estimator prices each survivor in isolation.

Never combines candidates; their savings are non-additive.

Packager

plan builds the scenarios and prices them with the stateful bundle estimator; assemble turns each warehouse into one frozen RecommendationPackage.

Never changes a candidate's decision.

Reviewer

A fail-fast invariant gate (Reviewer). It raises on the first violated rule and changes no decision, ID or economics. A rejection aborts the run.

Never repairs.

Reporter

run writes what it was given and counts it. Nothing is recalculated.

Never reads its outputs back into a decision.

The order inside the Optimizer matters: migration reads the auto-stop decision, and the rollback rewrites decisions already made. Every knob is decided before the scope filter runs, so cross-technique holds are the same in every scope. Chapter Techniques has the rules.

The two Reviewer gates

The candidate gate (review_candidates) checks each warehouse's candidates: one per in-scope knob, identity and epoch consistency, configuration limits, cost and confidence rules. The package gate (review_package) first re-runs the scenario checks (review_plans), then review_contract: the package's semantic validate(), a check that the published cost profile carries exactly the thresholds its name applies, and the committed Draft 2020-12 JSON Schema (validate_locked_package_schema).

Gate logging

A rejection logs the warehouse identity and a short rule label only. Gate messages and schema errors can embed values, so the full text never reaches the log.

Package write order

A package's ID is a hash of its content, so the order of operations is fixed and every step depends on the one before.

  1. Assemble

    _build_locked_recommendation_package builds the frozen package with a placeholder PKG-000… ID.

  2. Set the ID, then the full hash

    The ID becomes expected_package_id(); then provenance.package_hash_full_sha256 gets the full SHA-256 of the same hash payload. Volatile metadata such as generated_at is not in the payload.

  3. Semantic validation

    package.validate() checks cross-field rules the schema cannot express.

  4. Schema validation

    The package gate validates against the committed schema; the Reporter validates again just before writing.

  5. Serialize and write

    package_locked_contract writes packages/<workspace>__<warehouse>.json with sorted keys, then evidence.json, workbook.xlsx (unless disabled) and manifest.json.

A failed validation raises before the file is written, so a run never leaves a package on disk that does not match its own hash or the schema.

Boundaries enforced by tests

The CLI is an adapter

run parses its own flags, creates the run folder and log, builds the PublisherRequest and calls publish. Input mistakes it can see on its own are refused before anything is collected: --demo together with --from-evidence, and --flat-output into a folder that already holds packages/ or manifest.json, which would mix two runs' files. It never imports a capability package; tests/unit/publisher/cli/test_cli.py checks this. main maps a PublisherError to exit status 2 and re-raises anything else as a bug.

Shared access is neutral

OAuth, GET-only REST and the UTC-pinned SQL client live in src/workflow_shared/, which imports neither product (tests/unit/workflow_shared/test_boundaries.py). The Publisher passes its identity in PUBLISHER_ACCESS.

Check yourself
Where would you add a rule that holds a size cut when spill is high?

In the size technique inside the Optimizer (optimizer/techniques/size.py), reading a fact the Analyzer computes. The Analyzer observes, the Governor gates eligibility, the Optimizer decides; mixing them breaks the layering.

The candidate gate finds two candidates for the same knob. What happens?

It raises, the run aborts and nothing is written for that run. Gates verify and never repair, so a broken invariant is a bug to fix, not a case to patch over.

Why can't the PKG- ID be set before the package is complete?

The ID is a hash of the package's identity payload (versions, epoch, configuration, evidence fingerprint, ordered candidate and scenario IDs and more). It can only be computed once those are final; the full hash comes from the same payload.

A run is scoped to auto-stop only. Does the Optimizer still decide size?

Yes. Every knob is decided first so cross-technique holds behave the same in every scope; the scope filter then drops the out-of-scope decisions. A canary rollback is kept in every scope.

03Publisher

Evidence and configuration epochs

Every decision starts from evidence the collector reads out of Databricks system tables and normalizes into one WarehouseEvidence per (workspace_id, warehouse_id). The evidence is cut into configuration epochs, because a metric only describes the configuration it was measured under. Getting the epoch right is what keeps a recommendation from being judged on the wrong configuration.

Where the facts come from

The collector (extract_evidence) runs each read-only query once over the whole fleet and assembles the rows. It is the only place raw rows become typed evidence, and it logs counts and IDs only: never SQL text, owner emails, tags or configuration values.

System tableWhat the Publisher takes from itQuery module
system.compute.warehousesConfiguration snapshots: type, size, min and max clusters, auto-stop, channel, name, tags. The authority for epochs.config_epochs.py
system.compute.warehouse_eventsStarts, stops and scaling: running and idle time, cluster levels, restarts, running-idle gaps for every auto-stop value, the daily resource series.events.py
system.query.historyPer-query latency, queueing, spill, failures, concurrency and the workload mix from query_source (dashboard, job, notebook, Genie, alert) and client_application. Statement text is never exported.query_history.py

system.billing.list_pricesThe list price of each SQL SKU. Usage with no price stays unpriced, so its cost is null.billing.py

REST is used read-only for two things: resolving and validating the SQL execution target, and optional workspace compatibility evidence for a type migration (collect_workspace_compatibility_evidence). AWS cost for Pro and Classic comes from a committed EC2 on-demand price registry (model_aws_baseline_cost).

The normalizer cleans what the tables leave ambiguous: size names (normalize_size), redacted owners (clean_owner), the workload mix (derive_query_source_profile) and Photon. Photon has no configuration field in the snapshot table; infer_photon_observation infers ENABLED, DISABLED, MIXED or UNKNOWN from the current epoch's signed DBU split, and only when coverage, volume and freshness are good enough. The result is reported, never used as a recommendation input.

Configuration epochs

system.compute.warehouses writes a snapshot whenever any property changes, including the name or tags. The epoch query folds cosmetic snapshots into the surrounding period and starts a new epoch only when a decision field changes: type, channel, size, min clusters, max clusters or auto-stop. Renaming a warehouse therefore never resets its history. The current epoch is the open one; its ID enters every candidate, scenario and package hash.

The three exceptions to "current epoch only"

Older epochs are calibration and backtest material. They never choose a change, its target or its economics, with three narrow exceptions.

1 · Older peak holds a cut

If an older epoch of the same warehouse within the last 365 days reached more clusters of peak demand than the recent window, capacity cuts wait (OLDER_EPOCH_PEAK_DEMAND_HIGHER). Each older epoch's sustained peak (the level held for 30 busy minutes) is compared with the recent peak in clusters at 10 queries per cluster. Computed in Analyzer.

2 · Evidence a change cannot affect

A change to auto-stop or cluster limits does not change how heavy each query is. So when the current epoch is younger than the 30-day query window, demand and per-query evidence is read back to the last size, type or channel change, and capacity queueing back to the last change of size, type, channel, min or max clusters (PERIODS_CTE). The fields that carry are listed in DEMAND_CARRY_FIELDS and QUEUE_CARRY_FIELDS; carried_query_view lays them over the current epoch's.

3 · Canary rollback

After a canary-type change (one size down or a lower minimum), canary_observation compares the current epoch with the one immediately before it. A tripped fail-fast guard makes the Optimizer recommend restoring the previous epoch's value (canary rollback).

Never carried

Running time, idle time, cluster-minutes and billing always come from the current epoch alone. They are what a configuration change actually changes, so mixing in an older epoch would price the new configuration with the old one's behavior. Cold-start wait also never carries, because auto-stop changes it.

Settled billing and readiness

Billing arrives late and is sometimes corrected. A UTC day counts only 24 hours after it ends and once the account's billing watermark has passed it (billing_check_through). When a warehouse simply stopped running, its workspace watermark stalls at the last usage; effective_billing_watermark uses warehouse events to tell "no usage" from "usage not ingested yet", and keeps the workspace watermark when it cannot tell. --billing-ingested-through pins billing to what was ingested by a date, so a re-collection reproduces an earlier run.

Before any size, cluster or auto-stop change is decided, the current configuration needs 2 settled billed days (ready_billed_days). Readiness counts billed days rather than calendar age, so a warehouse that rarely runs is not judged on days it did nothing. Epoch age itself is computed from the analysis time, never the wall clock (epoch_age_days).

evidence.json and replay

Every run writes the normalized evidence it decided on to evidence.json (a live run writes it twice, the second time with the same bytes: first right after extraction, so a later refusal or crash still leaves a replayable file, then with the finished run): a versioned envelope with evidence_format_version 1.0.0, the Publisher version and the list of warehouses (save_evidence). It is validated against schema/evidence.schema.json before it is written and again when --from-evidence loads it (validate_evidence_payload). Any other version, or a bare list, is rejected; there are no legacy shims.

publisher --from-evidence ./demo_out/evidence.json --output-dir ./replay_out

A replay needs a readable evidence file: a missing path, a directory or an unreadable file is a refusal (exit status 2) that names the file, not a traceback, and a run is either replayed or simulated, so --demo with --from-evidence is refused as well (load_evidence_files).

Because decisions are deterministic, a replay of the same evidence under the same versions produces byte-identical packages. That makes the file the unit of reproduction for bug reports and the input of the golden cases.

Sensitive file

evidence.json holds owner emails and warehouse tags. Validation errors name the failing path and rule, never the value, and the loader logs counts and IDs only. Treat the file like any other export containing personal data.

Check yourself
An owner renames a warehouse. Does it get a new epoch?

No. Only decision fields (type, channel, size, min and max clusters, auto-stop) start an epoch; name and tag snapshots fold into the surrounding period, so history and readiness are kept.

Auto-stop changed nine days ago. Which period does the p95 execution time come from?

From the last size, type or channel change, clipped to the 30-day query window: auto-stop cannot change how long a query runs, so that evidence carries across the change. Idle time and billing still come from the nine-day current epoch only.

Can an older, busier epoch make the Publisher recommend more clusters?

No. An older peak can only hold a capacity cut. Older epochs never choose a change, its target or its economics.

Why is readiness counted in billed days and not calendar days?

A warehouse that runs twice a week would otherwise look "ready" after days of no activity. Settled billed days count only days the configuration actually ran and was billed.

04Publisher

Techniques and decision rules

The Optimizer turns the Analyzer's facts into exactly one decision per knob. Each decision is a pure function of the current epoch's evidence and the thresholds of the warehouse's cost profile: no wall clock, no randomness, no guesses. A missing fact never reads as "no pressure"; it becomes a blocker code code and the change waits.

One decision per knob, in a fixed order

Optimizer.optimize calls the techniques in the order size, max clusters, min clusters, auto-stop, migration, and each appends exactly one decision. The order matters once: the migration technique reads the auto-stop decision, because a warehouse that runs with no queries needs a human review before any migration experiment. One decision per knob holds by construction, which is the invariant the candidate gate checks.

Every technique first asks whether the configuration is ready. A decision is "young" when the current configuration epoch has fewer than 2 settled billed days (readiness_min_billed_days); young evidence holds a change with CURRENT_CONFIG_EPOCH_TOO_NEW. The thresholds themselves come from thresholds_for_profile, so an aggressive or conservative profile only moves the risk-appetite levels of cuts.

After the techniques run, in_scope keeps the knobs in the run scope and always keeps a canary rollback, since a rollback is a safety action.

ACTIONABLE

Apply with human approval. The evidence is direct enough that no test is needed (a lower auto-stop, a max-cluster change, a rollback).

TEST_REQUIRED

A canary: the effect is modeled, not observed, so the change is applied as a test and judged on its new epoch (size, a lower floor, a migration, a higher auto-stop).

NO_CHANGE

The current value stays. Blocker codes say what held a change, or the list is empty when today's value is already right.

INSUFFICIENT_EVIDENCE

The evidence a rule needs is missing, thin or too young. Nothing is priced.

BLOCKED

A change is warranted but a hard limit or guard refuses it (largest size, max-cluster limit, failures).

REVIEW

A person must decide first, for example whether a warehouse that ran with no queries is still needed.

Warehouse size

size.decide looks for spill first. Spill must be both frequent (at least 2.0% of queries, spill_query_pct_upsize) and severe (a p95 of spilled bytes among the spilled queries at or above spill_p95_bytes_upsize), backed by at least 20 spilled queries. Frequency without a reported severity is INSUFFICIENT_EVIDENCE. When 80.0% or more of the spilled bytes come from the top 3 statement sources, the fix is a rewrite of those statements, so the size stays (SPILL_CONCENTRATED_IN_FEW_STATEMENTS).

Without an upsize signal the technique tries one size down, and every safety signal can veto it: spill above spill_query_pct_downsize_safe, queueing above queue_query_pct_safe, failures above failure_cancel_pct_downsize_safe, p95 and p99 latency limits, fewer than 500 executed queries, growing query volume, a peak in the current epoch above the recent window, or an older epoch that peaked higher. A batch warehouse (job queries at least 80.0% of the load) is judged on 20 run days instead of the query sample and the latency limits.

Why a resize is never ACTIONABLE

The speed-up or slowdown of a resize and its cost are modeled, never observed. A resize also invalidates the max- and min-cluster decisions, which were measured at the old size, so they wait for a re-measurement.

Max clusters

decide_max_clusters raises the ceiling only when three signals agree: queued queries at or above 5.0%, a capacity-wait p95 at or above queue_wait_p95_ms_increase_max, and time at the ceiling at or above 5.0% (time_at_max_pct_saturated). For Pro and Classic the target comes from demand in one move:

Pro/Classic ceiling targetscaling.py
required = ceil( Pmax_cluster_target_percentile(running + queued queries per busy minute) / QUERIES_PER_CLUSTER_PRO_CLASSIC ) target = min( MAX_CLUSTERS_SUPPORTED_LIMIT, max( min_clusters, required + max_cluster_target_headroom_clusters ) )
percentile = 99.5 queries per cluster = 10 limit = 40 headroom = 1
Serverless scales differently, so its increase is one cluster at a time, and its confidence is capped by confidence_cap_serverless_ceiling_increase (0.59).

A decrease needs an unused ceiling: time at the ceiling at or below time_at_max_pct_safe_reduce, low queueing, a mature epoch and no evidence blockers. The new ceiling never drops below the recent window's observed peak, and the whole current epoch's peak holds the cut when it is higher than what the recent window shows (PEAK_OUTSIDE_RECENT_WINDOW), so a quarter-end peak is not cut away. On Serverless the new ceiling is that peak plus headroom: at least max_cluster_headroom_clusters (1) or max_cluster_cut_headroom_pct (25.0% of the peak), whichever is larger. The percentage is a cost-profile field, so a looser profile cuts to a lower ceiling and a stricter one keeps more room. The cut is ACTIONABLE with objective COST_GUARDRAIL: a lower ceiling caps runaway cost, but on a warehouse that never reaches it, it saves nothing directly.

Min clusters

decide_min_clusters sizes the floor by what it actually does: it carries the first minutes of a busy period until the autoscaler adds clusters. The target is the smallest floor that covers the busy-start demand at the min_cluster_busy_start_percentile percentile (95.0). It needs at least 20 busy periods, and it is held when the warehouse sits at its ceiling a lot (time_at_max_pct_block_min_reduce) or rarely at its floor (time_at_min_pct_reduce). Every proposal carries SPARE_FLOOR_CAPACITY_UNPROVEN because its saving is an upper bound the canary measures.

Auto-stop

The Analyzer scores every value on the type's grid against the warehouse's measured running idle gaps in _auto_stop_options; autostop.decide then chooses.

Net saving of one auto-stop valuefindings.py
lower value: net = removable running cluster-minutes − additional starts × restart_cost higher value: net = avoided starts × restart_cost − added idle cluster-minutes restart_cost = restart_cost_cluster_minutes_pro_classic (or _serverless) × floor clusters
restart cost per start: Pro/Classic 4.0 cluster-minutes, Serverless 0.1 cold-start budget: added starts ≤ 2.0% of queries (the balanced value; the cost profile sets it, none for Serverless) near-best band: within 2.0% of the best net saving, then the smallest change from today
A gap counts as removable only inside RUNNING time, so idle that the warehouse never paid for is never "saved". Choosing the smallest change inside the near-best band keeps the move conservative when several values save about the same.

A lower value is ACTIONABLE: its saving rests on observed idle time. A higher value saves only restarts, and whether starting minutes are billed is an assumption, so it is TEST_REQUIRED with RESTART_BILLING_UNVERIFIED. A Serverless warehouse set below the console's lowest value through the API is left alone. Activity that keeps a warehouse running with no query (open sessions, keep-alive) is flagged on every outcome and never priced.

Warehouse-type migration

migration.decide proposes Serverless to PRO or Pro/Classic to SERVERLESS as a TEST_REQUIRED canary, priced with a pre-canary DBU and AWS counterfactual (see the estimation chapter). It invalidates all four other knobs, because every one of them was measured on the old type. When system tables have not shown the target type in the workspace, the decision carries a capability blocker such as SERVERLESS_WORKSPACE_CAPABILITY_NOT_CONFIRMED_FROM_SYSTEM_TABLES. Unsupported types never get here: the Analyzer fails closed on them.

Canary rollback and conflicts

After a canary-type change (one size down or a lower minimum), canary_observation compares the new epoch with the one just before it, for at most 30 days after the change. A guard trips only when a metric is both above its safe level and more than 25.0% (canary_p95_regression_pct) worse than before, with a minimum sample: failures, queueing, spill after a downsize, or p95 execution time on statement sources seen in both epochs (at least 300 queries).

When a guard trips, apply_canary_rollback rewrites the decisions in place:

  • The changed knob becomes an ACTIONABLE PERFORMANCE decision that restores the previous epoch's value, with CANARY_GUARDRAIL_BREACHED plus the tripped guard codes. No saving is claimed. This is the only place an older epoch's configuration sets a decision.
  • Cuts that conflict with the restore become NO_CHANGE with CANARY_ROLLBACK_PENDING: after a size rollback, lower cluster values; after a floor rollback, a lower ceiling or a smaller size. An increase for queueing or spill is never held.
  • The planner puts the rollback first in every plan, and every run scope keeps it.

The value gate

A decision says what should change; the candidate estimator then prices it, and Estimator._value_gate holds a cost change that does not pay for itself. The held candidate keeps its modeled economics, so the reason stays visible.

Cost changes

A change made to save money (objective COST) is held when its own base savings are not positive (COST_CHANGE_NOT_COST_EFFECTIVE) or below 500.0 a year (cost_change_min_annual_savings, COST_SAVINGS_BELOW_MATERIALITY). An ACTIONABLE cost change with no price waits for its price; an unpriced canary is not gated, because the canary will measure it.

Migrations

A migration is held only when even its best case, the high end of total savings, is not positive (MIGRATION_NOT_COST_EFFECTIVE). Total only: Serverless DBUs include compute that Pro and Classic pay as AWS, so DBU alone is not comparable across types.

Observed, never recommended

Photon and the warehouse channel appear in current_config but no technique changes them. Photon's state is inferred from current-epoch billing (product_features.is_photon) by infer_photon_observation; Databricks publishes no Photon on/off price for SQL warehouses, so any saving would be a guess. A channel move has no priced effect. Their technique IDs are reserved and never emitted.

Check yourself
A warehouse shows no spill, no queueing and fast queries. Why might the size still be NO_CHANGE?

Absence of pressure is necessary, not sufficient. The downsize also needs a strong query sample (or enough batch run days), a ready epoch, no growth, no failure spike, and no peak in the current or an older epoch that the recent window does not show. Missing evidence for any signal is itself a blocker.

Why is lowering auto-stop ACTIONABLE while raising it is TEST_REQUIRED?

A lower value saves observed idle time inside RUNNING segments. A higher value only saves restarts, and the restart cost assumes starting minutes are billed, which is not documented, so the billed cost must be measured after the change (RESTART_BILLING_UNVERIFIED).

The run scope is current:auto-stop, yet the package contains a size rollback. Is that a bug?

No. Every knob is decided first and the scope filters afterwards, but in_scope() always keeps a decision carrying CANARY_GUARDRAIL_BREACHED: a rollback is a safety action.

A max-cluster cut is ACTIONABLE. How much does it save?

Nothing is claimed. A cut is a COST_GUARDRAIL: it never drops below the observed peak, so it removes no running time; it limits what a runaway workload could cost.

Estimation math

The Publisher prices in three layers. The candidate estimator prices one change as if it were the only one. The stateful bundle estimator prices a scenario step by step, each step acting on what the previous steps left. The package reports an package envelope over the scenarios. All three use the same Low, base, high convention, keep DBU and AWS cost apart, and publish null, never zero, for a cost they cannot know.

Three tracks, and why they cross

Every modeled cost is computed on three tracks, conservative, base and optimistic. They differ in how much of a modeled effect actually shows up: the realization factors 0.5, 0.75 and 1.0 (realization_conservative, realization_base, realization_optimistic). The optimistic track has the lowest cost and therefore the highest savings, so the ranges cross: savings low pairs with cost high.

Signed savings from a cost rangeSavingsModel._delta_range
savings.low = baseline − cost.high (conservative track) savings.base = baseline − cost.base savings.high = baseline − cost.low (optimistic track)
auto-stop, DBU, ge12: low = 18,045.54 − 15,706.30 = 2,339.24 ✓ base = 18,045.54 − 14,536.69 = 3,508.85 ✓ high = 18,045.54 − 13,367.07 = 4,678.47 ✓
Savings are signed: a negative value is a cost increase, which happens on purpose for a capacity increase and by accident on a pessimistic track. The total is DBU plus AWS on each track, and becomes null when either side is unknown.
Not a probability interval

Low and high are what the model yields when the effect realizes at the conservative or the optimistic rate. They are scenario bounds, not percentiles of a distribution. Unknown is null, never 0.

The forward baseline

Every saving is measured against the forward baseline: what the warehouse would cost over the next 365 days with no change. Modeler.forecast_from_daily_cost builds it from the current epoch's settled, watermark-covered billing days only.

Run-rate forecastmetrics.py
rate = the daily cost series cut to whole weeks (no weekday/weekend bias) daily = w × mean(last forecast_recent_days) + (1 − w) × mean(last forecast_long_days) w = forecast_weight_28_long with a full long window, forecast_weight_28_mid with at least the recent window ratio = clamp( mean(last 28) / mean(previous 28), trend_ratio_floor, trend_ratio_ceiling ) trend = 1 + trend_adjustment_weight × (ratio − 1) forecast_365 = daily × trend × 365
windows 28 and 84 days w = 0.65 or 0.75 ratio clamped to [0.75, 1.25] trend weight 0.25 ge12 forward cost: DBU 18,045.54 + AWS 10,244.70 = 28,290.24 USD
The trend is damped twice: the ratio is clamped, then only trend_adjustment_weight of the change moves the forecast. A warehouse that doubled last month is not projected to double again.

Periodic workloads, such as a month-end close, would look like noise to a run rate. billing_cadence detects short runs (billed days at most 3 days apart belong to one run) resting longer than 7 days, and then uses the cadence model: the cost of whole run-to-run cycles divided by their days, times 365, with no trend. It needs at least 2 whole cycles.

When the forecast cannot be known it is null, and dbu_forecast_status says why: UNPRICED_USAGE (a DBU row with no list price), INSUFFICIENT_ACTIVE_COST_DAYS (fewer than 7 billed days), NON_POSITIVE_RUN_RATE or INSUFFICIENT_BILLING_CYCLES. Every candidate estimate scales this baseline, so a null baseline withholds them all. The AWS forward cost is modeled from running cluster time with the same blend, so DBU and AWS describe the same year.

Candidate estimator: one change at a time

Estimator turns each decision into cost factors on the forward DBU baseline, one per track, in CostModel._factors. A factor below 1 is a saving. Each candidate is priced against the same baseline as if it were alone, which is why candidate savings are Non-additive and carry candidate_savings_must_not_be_summed.

Auto-stop

The reclaimable running cluster-minutes per day at the target value, as a share of today's running cluster-minutes. Only the idle a lower value removes is scaled by realization; restarts count in full on every track.

share_r = min(1, realized × r + fixed), factor_r = max(0, 1 − share_r). Lower: realized = gain, fixed = −loss. Raise: realized = 0, fixed = gain − loss.

Min clusters

Spare floor capacity from floor_spare_shares: each running minute at the floor whose demand needed d clusters holds floor − max(k, d) clusters a floor of k would remove, with d = ceil((running + queued) / QUERIES_PER_CLUSTER_PRO_CLASSIC).

factor_r = max(0, 1 − spare_share × r). Spare and running minutes are annualized the same way, so the trend cancels.

Size

factor_r = capacity_ratio × (busy_share × multiplier_r + 1 − busy_share), clamped to [0.05, 3.0]. A downsize slows busy time by 1.1, 1.3 or 2.0; idle time does not change.

The capacity ratio is the published Serverless DBU per hour, or for Pro/Classic the workspace's own billed rates (the median billed DBU per running cluster-hour by size across the workspace's Pro/Classic epochs, which _prepare_workspace_calibration collects; older epochs only calibrate here, they never choose a change), accepted only within 0.25 of the published size ratio (validated_size_rate_ratio). Otherwise the estimate is withheld (PRO_CLASSIC_SIZE_RATE_UNVERIFIED).

Max-cluster increase

Optimistic adds nothing: the same queries finish on more clusters at once. Worst case: every added cluster runs whenever the warehouse sat at its ceiling, raw = minutes_at_max × Δclusters / cluster_minutes. Base for Pro/Classic: only the clusters each busy minute's demand needs under the new ceiling, from the concurrency histogram.

factor = (1, 1 + base, 1 + raw). A ceiling cut is a guardrail with factor 1.

Migration

CostModel._migration_costs prices the target type at the current size, running at its own best auto-stop: DBU = target cluster-minutes / 60 × DBU per hour × unit price ÷ reconciliation.

The same formula must reproduce today's billed forecast within [0.7, 1.3] (MIGRATION_MODEL_NOT_RECONCILED otherwise), so systematic model error cancels. Serverless AWS is a true zero: its infrastructure is inside the DBU line.

No change, blocked, unknown

NO_CHANGE and the max-cluster guardrail have factor 1, so their savings are a real 0. BLOCKED, INSUFFICIENT_EVIDENCE, a rollback, a missing baseline or an unvalidated rate have no factor: the economics are null and estimate_blocker names why.

AWS reuses the DBU factors for every knob except size, where it uses the EC2 cluster-hour ratio times the runtime multiplier (_aws_factor_range).

Scenarios: the stateful bundle estimator

Two changes to one warehouse overlap. Auto-stop and a lower floor both remove running cluster-minutes, and a minute cannot be saved twice. StatefulBundleEstimator therefore walks the plan in order, carrying a state of DBU, AWS and resource tracks (_ChainState), and applies each candidate's bundle_effect to what the previous steps left.

idle_cluster_minute_reduction

Auto-stop. Removes (realized × r + fixed) × today's running minutes from the resource track, less any overlap with an earlier floor cut, and scales DBU and AWS by the share removed.

min_cluster_reduction

A lower floor. Claims the spare floor capacity minus the wall-clock minutes an earlier auto-stop already removed per floor cluster, realized per track. The floor track keeps the part of the cut it did not realize.

multiplicative_cost_factor

Size or a ceiling increase. The runtime part moves running time by a fixed amount, after = before + acted × (rf − 1); the price part (factor / rf) applies as a ratio. This keeps the total independent of step order.

Three more effects complete the set: migration_cost_override replaces the state with the migration's pre-canary costs; requires_canary and estimate_withheld halt the chain, so every later figure is null; no_cost_change does nothing.

Policy, cost profiles and run scope

Policy is the set of numbers that decides how much evidence is enough and how much risk a cut may take. It lives in one frozen object, Thresholds, owned by the Governor. Cost profiles adjust a small part of it per warehouse, and a run scope limits what gets recommended. Databricks platform facts sit beside the policy and are never adjusted.

Thresholds: one frozen policy object

Thresholds is a frozen dataclass with 104 fields: evidence floors (how many queries, how many settled billed days), pressure limits (queueing, spill, latency), estimator parameters (forecast weights, realization factors), confidence weights and caps, and planner risks. The Governor owns it; every technique and estimator receives the instance it should use instead of reading globals. Its __post_init__ refuses confidence weights that do not sum to one, and derived caps such as confidence_cap_default are properties computed from the cut-offs, so a cap can never drift above the level it is meant to keep a candidate below.

A change to any default changes decisions. The repo treats it like a code change to an algorithm: bump the affected component versions in src/publisher/config/versions.py, regenerate the golden cases, and update the row in thresholds.md. A test compares that document's defaults with the dataclass, so the two cannot drift.

Rule

Prose names a parameter; only the dataclass and its reference page hold the number. When you need a value in code, read it from the Thresholds instance you were given. A literal such as 500 in a technique would escape both the cost profile and the version bump.

Cost profiles

Every warehouse is evaluated under exactly one cost profile: conservative, balanced or aggressive. Balanced is the dataclass defaults. The other two replace only the fields named in COST_PROFILE_GROUPS, grouped by technique, with the values in _OVERLAYS. thresholds_for_profile returns the base instance for balanced and a dataclasses.replace copy otherwise, so every field outside the groups is identical under all three profiles.

may change

How much measured pressure a cut may tolerate (spill, p95 and p99 latency, queueing, time at the floor or ceiling), the added cold-start share a lower auto-stop may cause, the canary rollback margin, the growth hold, and the materiality floor of the value gate (cost_change_min_annual_savings). A few fields also set how deep a target goes: the headroom a Serverless ceiling cut keeps above the peak, the busy-start percentile that sizes a minimum-cluster floor, and the cold-start budget that bounds how low an auto-stop may go.

never changes

How a warehouse gets its profile (assign_cost_profiles), first match wins:

  1. A per-warehouse flag, --cost-profile aggressive=wh-demo-005 (a bare warehouse ID, or workspace_id/warehouse_id when the ID exists in several workspaces). A reference that names no collected warehouse stops the run instead of silently falling back.
  2. An all-warehouse flag, --cost-profile conservative.
  3. The tag default: a current-epoch tag whose key is in nonprod_tag_keys (env, environment, stage, tier) and whose value is in nonprod_tag_values selects aggressive (nonprod_tag_match).
  4. Otherwise balanced.

Flags are parsed by the config layer (parse_cost_profile_flags), which rejects an unknown profile or one warehouse given two different profiles.

The package records the choice in cost_profile: the name, the source (CLI_WAREHOUSE, CLI_ALL, TAG_DEFAULT or DEFAULT), the source detail and the effective applied_thresholds (applied_thresholds). The example warehouse ran as balanced with source DEFAULT, so its cold-start budget is 2.0% and its materiality floor 500.00. Under conservative the same floor would be 1,000.00, under aggressive 250.00.

Why the profile is hashed

The profile name and its applied thresholds are inputs to the candidate, scenario and package IDs. The same evidence evaluated under two profiles produces different IDs even when every decision happens to match, so a package always states which risk appetite produced it. The package gate re-derives applied_thresholds from the name and refuses a package whose values disagree (review_contract).

Eligibility and the supported-type gate

The Governor decides what the Optimizer may consider (govern). Its one hard rule is fail closed: only CLASSIC, PRO, SERVERLESS (standard Serverless) are analyzed (SUPPORTED_WAREHOUSE_TYPES, checked by _is_supported_warehouse). A live run also checks the AWS price registry before anything is decided (aws_region_price_guard). Check yourself
A warehouse is tagged env=dev and the run passes --cost-profile conservative. Which profile applies?

Conservative. An all-warehouse flag beats the tag default; only a per-warehouse flag would beat that flag. The package's cost_profile.source reads CLI_ALL.

The same change is priced the same under every profile. How can a looser profile still save more?

Because the profile changes which change is recommended, not how a change is priced. A change (the same current and recommended value) has the same low, base and high savings under conservative, balanced and aggressive, since profiles never touch estimator or forecast parameters. A looser profile saves more in three ways. It ships cuts a stricter profile holds. It chooses a deeper target where the profile moves the target: the Serverless ceiling-cut headroom, the busy-start percentile that sizes a floor, and the auto-stop cold-start budget (1.0% of queries when conservative, 2.0% balanced, 10.0% aggressive). And it lets smaller savings pass the materiality floor (1,000.00, 500.00 and 250.00 a year). The one estimator exception is the Pro target of a Serverless-to-Pro migration, priced at its best auto-stop within the profile's cold-start budget.

Replaying the demo fleet's saved evidence under each profile shows all three effects. The auto-stop of wh-demo-027 is held at 30 minutes under conservative and balanced and goes 30 to 10 under aggressive. That of wh-demo-039 goes 365 to 210 under conservative and balanced but 365 to 15 under aggressive: a deeper target, hence a larger saving, and a different change. Where the target is the same, as for wh-demo-006 (15 to 10 under balanced and aggressive, held by conservative), the estimate is identical. See thresholds.md, Cost profiles.

A run is scoped to migration, but the size canary from last week tripped its p95 guard. What does the package contain?

The migration candidate, plus the size rollback listed in run_scope.safety_inclusions. The rollback is kept because in_scope never drops a decision carrying CANARY_GUARDRAIL_BREACHED, and the recommended scenario becomes an in-place scenario holding only that rollback.

Why is the auto-stop floor in PRODUCT_CONSTANTS and not in Thresholds?

It is a documented Databricks limit, not a risk choice. Keeping it out of Thresholds means no cost profile and no policy version can push a recommendation below what the platform accepts.

The RecommendationPackage is the Publisher's only public answer: one JSON document per warehouse and current epoch, schema-validated, content-addressed and frozen. Everything else, the workbook included, is a projection of it. Learn to read it and you can audit any recommendation without running the code.

The top-level blocks

The schema requires 18 top-level fields. Three of them may be null (observed_change, carried_forward_plan, run_scope); every other field is always present, so a consumer never has to guess whether an absent key means zero, unknown or not applicable. Grouped by the question they answer:

Which warehouse, which epoch

recommendation_package_id, contract_version, warehouse (with current_epoch), current_config.

What we know

workload_profile, cost_baseline, assessment, evidence, observed_change.

What we recommend

candidates, scenarios, recommended_plan, package_economics.

Under which policy

cost_profile, run_scope, provenance (every component version and the hashes).

After the change

realization, always NOT_APPLIED with no records when published; the Realizer keeps its own records.

Reserved

carried_forward_plan, always null in current producers.

Never add candidate savings

Each candidate is priced alone against the same no-change baseline (is_additive is false). Auto-stop alone saves 5,500.87 and the size cut alone 7,918.71, but applied in sequence they save 11,219.65: once auto-stop has removed idle minutes, a smaller size has fewer minutes left to make cheaper. Only the scenario estimate combines steps.

Scenarios, steps and the recommended plan

A scenario is an ordered, mutually exclusive path. Plan A optimizes the current warehouse type in place; Plan B migrates the type. They are alternatives, so the owner follows one. Each scenario holds an execution_plan of steps. A step has a step_type (CANDIDATE, COMPATIBILITY_VALIDATION, REMEASURE) and an execution state:

  • READY: an ACTIONABLE change a person can apply now, like the auto-stop step.
  • READY_FOR_CANARY: a TEST_REQUIRED change applied as a canary and judged on the new epoch's own evidence, like the size step.
  • REQUIRED: a gate that is not a knob change: validate migration compatibility first, or re-measure and regenerate after a step that invalidates other knobs.

recommended_plan names the chosen scenario (scenario_id), why it was chosen (selection_reason_code: here CURRENT_TYPE_OPTIMIZATION_HAS_VALIDATED_EVIDENCE), what to do next (REVIEW_AND_EXECUTE_FIRST_READY_STEP) and whether a person must approve (requires_hitl = true; always true, because the products never apply anything). Its decision_summary is the one paragraph to read aloud in a review:

Decision summary of the example

Plan A — Optimize current warehouse type is the deterministic execution path; apply validation gates and regenerate after invalidating changes. Apply the ready no-canary steps (auto_stop_minutes) first; start the warehouse_size canary once the next run shows their new configuration ready (2 settled billed days), so the canary's cost reading is not mixed with their savings.

Economics fields and their meaning

Every money figure in the package follows the same rules (contract section 15):

  • DBU and AWS are separate components with a total; Serverless has no AWS component of its own. Unknown is null with an availability or estimation status, never zero.
  • Ranges have three tracks, Low, base, high. They are scenario bounds from conservative to optimistic realization, not a confidence interval.
  • Savings are signed: positive saves money, negative costs money. A low track can be negative, as the size step's is in the example.
  • Candidate economics are isolated and non-additive; scenario economics are stateful (each step acts on the state the previous one left); package economics are an package envelope over scenarios.

The envelope takes the lowest scenario low, the recommended scenario's base and the highest scenario high. In the example both bounds come from Plan A, because Plan B's range sits inside it:

Write order

The order is fixed so the ID and hash always describe exactly the bytes that are validated and written.

  1. _build_locked_recommendation_package assembles the frozen dataclass with a placeholder ID, replaces it with expected_package_id(), stores full_package_hash() in provenance, and runs the semantic validate().
  2. The Reviewer's package gate (review_contract) runs validate() again, checks that cost_profile.applied_thresholds match the profile's name, and validates against the committed schema schema/recommendation-package.schema.json.
  3. The Reporter (package_locked_contract) validates the serialized payload against the schema once more and writes json.dumps(payload, indent=2, sort_keys=True) to packages/<workspace_id>__<warehouse_id>.json, then evidence.json, the workbook and manifest.json.

Read a package in five minutes

  1. recommended_plan: the chosen scenario, the next action and the decision summary.
  2. That scenario's execution_plan, in step order: what changes, in which execution state, and where a canary or re-measure gate sits.
  3. Each candidate's status and blockers, including the NO_CHANGE ones; open evidence_refs when a decision surprises you.
  4. package_economics: low, base and high, the currency, and the excluded scenarios. Do not sum candidate savings.
  5. cost_baseline.forward_365d: the no-change cost the savings are measured against, and which components are available.
  6. assessment: overall_status and evidence_quality tell you how much to trust the rest.
  7. cost_profile, run_scope and observed_change: the risk appetite, the scope, and whether the configuration just changed.
  8. provenance: when comparing two packages, check the component versions first; a version change explains a decision change.

The full field reference is the Reporter JSON Contract; the semantic rules the schema cannot express are in its section 18.

Check yourself
Two runs over the same evidence, one with --scope current and one unscoped, produce different PKG- IDs. Is that a bug?

No. run_scope is part of the package hash payload, so the restricted package gets its own ID. The in-scope candidates keep the same CAND- IDs, because scope is not a candidate hash input.

Why is generated_at not part of the package hash?

It is volatile presentation metadata. Excluding it lets a replay of the same evidence reproduce the same ID and the same bytes, which is what makes golden tests and the Realizer's hash check possible.

A candidate's savings_365d.total is null. What does that mean, and what must a consumer not do?

The saving could not be priced (for example a missing price or too little cost history); the estimation status and blockers say why. A consumer must not treat it as zero or drop it from a total as if it were zero.

The package envelope's low and high both name Plan A. How can that be when Plan B has a higher base?

The envelope takes the lowest low and highest high across scenarios and the base of the recommended one. Plan B's whole range sits inside Plan A's, so both bounds come from Plan A, and the base comes from Plan A because it is recommended.

08Realizer

Realizer pipeline and math

The Realizer answers one question for one package: after an owner applied a recommended change, how much did it actually save? It reads one locked RecommendationPackage and an observation of the warehouse after the change, prices what the old configuration would have cost over the same days (the counterfactual), and appends what it learns to an append-only realization ledger. Like the Publisher it is read-only and deterministic: it never changes a warehouse and never edits the package.

One line of math, many gates

Realized saving = counterfactual old cost − observed new cost. Everything else in this chapter decides whether that number is trustworthy: may it be measured yet, was the change really the recommended one, did performance hold, is the counterfactual defensible, and may the saving be claimed for the recommendation.

The pipeline

realize_request calls each capability once, in order, and holds no domain logic, the same shape as the Publisher's publish(). Inputs are checked before anything is written (build_context), then the run holds the lock of its ledger until the Reporter has written. The first thing recorded is the lineage entry (REALIZATION_CREATED), so even a run that fails later leaves a ledger that says the package exists.

Analyzer

Turns the observation source into one normalized observation: plans the measurement windows (settled whole weeks after the change and the same span before it), runs the counterfactual for the changed knob and gathers guard metrics. The only module that runs Publisher SQL is bridge.py. A connector failure (a missing grant on a system table, a warehouse that does not start) becomes a one-line refusal naming the statement label, the exception class and the first line of its message, never the statement text (describe_exception).

Governor

Pure policy checks held lazily: readiness, the fail-fast guards, counterfactual eligibility and the financial-quality gates, all from RealizerPolicy and the package's own cost-profile thresholds.

Reconciler

Matches what the warehouse runs to the published plan (exact, modified, independent change), decides lifecycle events (application, drift, rollback, supersession, regeneration) and resolves ownership across the warehouse's lineages. It prices nothing.

Estimator, Reviewer, Packager, Reporter

The Estimator computes realized economics and attribution (calculate_economics, attribution_result). The Reviewer assembles the validation episode and the recognition status and cannot reject anything. The Packager appends ledger entries and projects the snapshot; the Reporter writes the files.

What it accepts from the Publisher

validate_package refuses any package that is not an unmodified Publisher package of the supported contract, before a single file is written. The checks run in this order:

  1. contract_version equals exactly 3.1.0 (SUPPORTED_PUBLISHER_CONTRACT). There is no range: a new Publisher contract needs a Realizer release.
  2. The package passes the Publisher's committed JSON Schema.
  3. The PKG- id and provenance.package_hash_full_sha256, recomputed from the hashed fields, match. A hand-edited package fails here.
  4. The realization block is the Publisher's empty NOT_APPLIED placeholder. The Realizer's own record is the RPKG, never this block.
  5. carried_forward_plan is null, the recommended scenario exists, the warehouse type is one of CLASSIC, PRO, SERVERLESS, and no plan step recommends its current value.

From an accepted package it reads the warehouse identity, current_config, the recommended scenario and its execution plan (step, knob, current and recommended value, execution state, dependencies, invalidations, running savings), each candidate's independent_economics, the evidence, cost_profile.applied_thresholds, run_scope, observed_change and the package currency. For the worked example the RPKG id follows directly: RPKG-95A326BCCB54E020E084ABD3 from PKG-A3B4D254A56722B52107A313.

Where the observation comes from

One observation source per run. Every mode ends in the same normalized observation, so the pipeline above never knows which one it got.

--demo

A simulated world for a Publisher demo-fleet warehouse: its first eligible step is applied a week after the package and measured four settled weeks later. --demo-modified applies a size step one size off, to exercise the modified path.

Live

--profile (OAuth only) with --sql-warehouse-id naming a collector warehouse. A single-package run refuses a collector that is the warehouse being measured, because its own queries would keep it running and pollute the measurement. A fleet run skips that one warehouse instead (below).

--from-evidence

Replays the measurement evidence file a live or demo run wrote under realization/measurements/, offline and byte-identical.

--observation

A ready-made normalized observation file, for tests and caller-supplied measurements.

--publisher-run

A fleet run over every warehouse of a Publisher run folder, one at a time, each failure isolated to its warehouse, then a run manifest and the realization workbook. In a live fleet run the collector warehouse is not measured: its run status is SKIPPED with a reason, and the exit status is unchanged (is_collector_warehouse). The run keeps one connection and reads the account-wide statements (configuration snapshots, the billing watermark, daily cost) once for all warehouses (LiveSession).

--backtest

Past auto-stop changes from system tables, with no package and no ledger: it checks the replay method against changes that already happened.

Counterfactuals per knob

A counterfactual prices the actual post-change days under the old value, holding every other knob at its observed value. That is why a workload change does not fake a saving: busier days cost more under both values.

Auto-stop: replay claim-eligible

The collector measures, for the post-change running time, how many idle cluster-minutes the old value would have added and how many restarts it would have avoided. Raising back to the old value costs added_idle − avoided_starts × restart_cost; replaying a lower value is the negative of removable − additional_starts × restart_cost. The restart cost is the package's assumption per start times max(1, min_clusters). replay_net_cluster_minutes

Size: runtime ratio claim-eligible

ρ is the post-change queries' execution time at post-change medians over the same queries at pre-change medians, per statement source seen in both windows. The old size's running minutes have two bounds from the observed R1: elastic R1 × (1 − b + b/ρ) and inelastic R1; the claim takes the smaller saving. The old size's measured price must sit within the published rate band. counterfactual_running

Min clusters: floor levels claim-eligible

From running minutes per cluster count: the counterfactual runs every level at least at the old floor, Σ minutes × max(n, old_floor), against the observed Σ minutes × n. A floor raise is never measured: minutes at the new, higher floor cannot say what the old floor would have run. floor_cluster_minutes

Max clusters no saving

A capacity add is a cost, priced as the cluster-minutes above the old cap and judged on performance. A cap cut yields only an upper bound of what the old cap could have added. above_cap_cluster_minutes

Migration observed only

There is no reverse model of what the old type would have billed for the new type's days, so the Realizer reports the bill's movement against the pre-change window carried forward (method CORRELATED_ONLY) and claims nothing (NO_REVERSE_MIGRATION_MODEL). migration_delta

Which methods may support a claim

Only CLAIM_ELIGIBLE_COUNTERFACTUAL_METHODS. The auto-stop replay records itself as CALIBRATED_PRIOR_STATE: the prior state's behaviour replayed on the observed days.

Fail-fast guards and readiness

A saving only counts if performance held. validate_performance applies the Publisher's own canary guard with the package's cost-profile limits. Each rule is PASS, FAIL or UNKNOWN; one FAIL fails validation, and an UNKNOWN means "not ready yet", never "failed".

The two-part rulepolicy.py
FAIL when post > safe level AND post > pre × (1 + margin%) with the minimum sample
REAL-FAIL-001 failure/cancel share safe 5.0%, margin 25.0% (every knob) REAL-COLD-001 added cold-start share budget 2.0% (auto-stop; Serverless has no budget) REAL-QUEUE-001 queued share safe 0.5% (other knobs) REAL-SPILL-001 spilled share safe 0.1% (size) REAL-P95-001 p95 on shared sources rise above 25.0% (other knobs)
Both parts matter: a metric that was already high before the change is not blamed on it, and a large relative rise from a tiny base is not a failure while it stays under the safe level. The Realizer policy can only tighten the p95 limit, never loosen it. These are the balanced defaults; the package's cost profile supplies the values actually applied.

Readiness (readiness) needs a minimum number of days and queries, a representative regime, sufficient evidence quality and no guard without evidence. A step that was a canary (READY_FOR_CANARY) stays provisional for the Publisher's guard window (CANARY_GUARD_WINDOW_DAYS).

Classifying the result

The checks run in a fixed order, and the first that applies decides. The order encodes priorities: a failed guard beats everything, an indefensible counterfactual is blocked before any comparison, and a currency or workload shift is reported but never judged against an expectation priced under other conditions.

The comparable volume band is the post-over-pre query ratio VOLUME_RATIO_BAND (0.75 to 1.25); the example's ratio is 1.008. The ratio thresholds of step 8 are policy fields of RealizerPolicy.

Which expectation is the denominator

denominator picks the expected annual savings to compare with:

  • One step applied exactly: that candidate's independent_economics.savings_365d (PUBLISHER_CANDIDATE). This is the example.
  • Several plan steps applied in order: the last applied step's projected_economics.running_savings_365d, the stateful scenario value (PUBLISHER_SCENARIO).
  • A modified auto-stop (the owner chose a different value): the package's own option grid re-prices the applied value by linear interpolation (REESTIMATED_APPLIED_SCOPE, method PACKAGE_OPTION_GRID).
  • A migration: the scenario's pre-canary range, informational only.

Attribution: may the saving be claimed?

Measuring a saving and claiming it for the recommendation are separate decisions. attribution_result collects hard disqualifiers; with none, a qualified origin and passing financial-quality gates, the claim is CLAIMABLE with HIGH_CONFIDENCE. Otherwise it is OBSERVABLE_ONLY (validated, but partially or only correlated) or NOT_ATTRIBUTABLE.

Financial-quality gates

Attributable spend at least 95%, price coverage 100%, currency consistency 100% and equal to the package's, a complete correction chain and the material cost components available. A gate whose input is null does not pass. economic_quality_result

Hard disqualifiers

Applied state unmatched, guardrail failed, no defensible counterfactual (or no reverse migration model), overlap with another scope, an independent change not held constant, canary window still open, billed cross-check disagrees, origin independent or not attributable, a performance or capacity step, or the change is owned by another lineage.

Origin

CONFIRMED when an approvals file names this package, the knob and the observed value; INFERRED when the knob changed after the package was generated; otherwise UNKNOWN, which cannot support the strict claim. An approval that confirmed no change of the run is logged as a warning, naming its position, package and knob, never its value (warn_unmatched). The example is INFERRED. origin

One owner per change

A warehouse can have several packages over time (lineages). Only one can own a given applied change; the others get CLAIMED_BY_OTHER_LINEAGE. ownership

Recognition is a third, separate status (recognition_status): REJECTED when a guardrail failed, CONFIRMED when the counterfactual is eligible and not provisional, PROVISIONAL otherwise. The example's attributed realized saving for the period is 564.91.

The billed cross-check

The replay is a model. The cross-check asks whether the bill agrees: it scales the pre-change billed cost per day by the volume ratio to the post-change days and compares the drop with the replayed DBU saving, against the week-to-week noise of the pre-change bill. It is the only statistical test in the Realizer.

Maturity, realized to date and corrections

Daily runs measure overlapping windows. realized_to_date gives each instant the value of the latest measurement covering it, pro rata, and sums the covered instants; a re-measured window replaces the earlier value for its days. Maturity follows the evidence (project_snapshot):

  • NOT_APPLIED no application observed; COLLECTING applied, nothing measured yet; PROVISIONAL measured but not ready.
  • REPRESENTATIVE measured with readiness passed, as in the example (28.00 days covered).
  • MATURE once measurements cover MATURE_DAYS (365) days; the trailing-twelve-month figure then fills mature_ttm_realized_savings.

Billing is restated sometimes. When a later run measures an already-measured window with different billing, the new measurement is recorded with a correction entry that points back at the one it replaces (correction_facts). Nothing is overwritten. The Realizer also never performs a rollback: "rollback" means it recorded a requested or observed return to the old value, or a later package that undid the change.

Check yourself
Why does the auto-stop replay run on the post-change days instead of comparing the month before with the month after?

A before-and-after bill comparison mixes the change with everything else that moved: more queries, different days. Replaying the old value on the observed post-change days holds the workload fixed, so the difference is the change alone. The before-and-after view survives only as the billed cross-check.

The example's annualized saving is above the published high. Why is it still plain REALIZED?

The replay measures the full mechanical effect, which is the optimistic track behind the published high. Only a result above 1.25 × high is flagged for review (REVIEW_ABOVE_HIGH). Anything at or above the low counts as realized.

A measurement passes every guard, but the query volume doubled after the change. What happens?

The saving is still measured, because the counterfactual prices the actual post-change days. It is classified MONITORING with WORKLOAD_SHIFT, never realized or under-realized, because the package's expectation was priced at the old workload. The cross-check also turns INCONCLUSIVE.

Why can a warehouse migration never be CLAIMABLE?

There is no model of what the old type would have billed on the new type's days. The observed delta uses the pre-change window carried forward (CORRELATED_ONLY), so anything else that moved the bill is inside it. The attribution carries NO_REVERSE_MIGRATION_MODEL and the claim stays observable only.

Realizer outputs, explained

The Realizer writes three kinds of JSON: an append-only ledger that is the history of one package's realization, a realization package (RPKG) that projects that history into a current view, and the measurement evidence a live or demo run collected, so the same measurement can be replayed offline. This chapter walks each one with the real files of the worked example.

Where the files live

Two roots. The state directory outlives runs and holds every warehouse's history. Each run also writes a fresh run folder with that run's projections. Reading the ledger again always reproduces the projections, so the history in the state directory is what you back up. resolve_layout

A fleet run also writes a run manifest (format 1.1.0) that lists, per warehouse, the status of its run and the files it wrote. The status is OK, REFUSED (an input the Realizer does not accept, with the reason), CRASHED (a defect, recorded by exception type only) or SKIPPED (not measured by design: the live run's collector warehouse). Its as_of_utc is the one measurement time the run used; a live run without --as-of fixes it when it starts.

Every Realizer ID is a content hash, built the same way as the Publisher's: a prefix plus the first 24 uppercase hex characters of a SHA-256 over canonical JSON (content_id). The realization package

The RPKG is the ledger folded into one current view (project_snapshot). Measurement evidence

A live or demo run first writes what it read from the system tables to state/realization/measurements/ (format 2.0.0), then projects the normalized observation from it (project_observation). --from-evidence replays that file and gets the identical result offline, which is how a measurement is audited or re-run under a new Realizer version. The guide trims the 365 daily billing rows to three.

  • epochs: the configuration timeline; the change is the boundary between the last two.
  • windows.pre and windows.post: settled whole-day windows either side of the change, with running time, restarts and the replay rows per candidate auto-stop value (the size runtime or cluster levels for other knobs).
  • daily_cost: billed DBU and list cost per day, including restated and unpriced quantities; the financial-quality gates are computed from it. A window in which the warehouse ran but that has no billed day has an unknown billed cost (null, never zero), and the step is not measured, reason BILLING_INCOMPLETE.
  • guard: guard metrics for the previous and current epoch; assumptions: the package's thresholds and restart costs the measurement used; aws: the modeled cluster-hour price per window.
Check yourself
You re-run the Realizer on the same day with the same evidence. What changes in the ledger?

Nothing. Every entry's id is a hash of its content, and an entry whose id is already in the ledger is suppressed. The run folder gets fresh copies of the same RPKG and snapshot.

Billing for an already-measured week is restated. How does the ledger show it?

A new measurement entry with the corrected economics and a corrects_entry_id pointing at the original. The original stays. Realized-to-date uses the latest measurement for each covered day.

Why does the snapshot id include the ledger checkpoint hash?

So a snapshot names exactly the history it was projected from. Two snapshots with the same id are guaranteed to rest on the same ordered entries and the same projector version.

Where would you look to audit the example's counterfactual cost?

The COUNTERFACTUAL_RECORDED entry gives the method, the cost and its assumptions. The measurement evidence holds the replay rows and the billed days it was computed from. --from-evidence on that file reproduces it.

The post-change running minutes by cluster count show one cluster all day; with the old floor every minute would have run three, which is the counterfactual. Measured after the canary's 30-day window.

There is no reverse model, so the change is observe-only: the billed change at the pre-change query mix is the observed delta (DBU up, the customer's AWS cost gone, a true zero on Serverless), reported against the informational migration range and never claimed.

Check yourself
The owner applied only step 1. Why is the realized saving compared with the auto-stop candidate's range rather than the scenario's total?

The scenario total includes the size canary, which was not applied. An exactly applied single step is judged against its own candidate's isolated savings; the denominator source in this package is PUBLISHER_CANDIDATE.

The annualized saving is above the published high. Why is it still REALIZED and not flagged for review?

A result at or above the published low is realized. Review is flagged only above 1.25 times the high (REVIEW_ABOVE_HIGH; 9,168.12 here), which this saving does not reach. The replay is the optimistic track of the published range, so landing near the high end is expected.

Why does the measured window start the day after the change instead of at the change time?

Billing settles by whole UTC days. The change day mixes two configurations, so it belongs to neither window; the pre and post windows are whole settled days of one configuration each.

What would make the claim OBSERVABLE_ONLY even though the saving is real?

Any hard disqualifier: another knob changed in the window, a failed financial-quality gate, a cross-check that disagrees, an open canary window or another lineage owning the change. The saving is still recorded; it just cannot be claimed for this recommendation.

Outputs and operations

This chapter is the operator's view: the commands that run each product in each mode, the folders a run writes, the workbook, the first live run on a real account, and the checks that keep a change honest. Both products only read the account; the one change in any workflow is the one an owner makes by hand.

Command recipes

Each product has one console script in front of a facade: the CLI parses and validates its own arguments, builds a request and calls the facade once. A refused input (an unknown scope name, a package that fails its hash check, a static token) exits with status 2 and a one-line message. A Realizer fleet run returns 1 if any warehouse crashed, else 2 if any was refused, else 0 (run_fleet); a warehouse that was skipped by design (below) changes neither. Mistakes the Publisher CLI can see on its own are refused before anything is collected: --demo with --from-evidence, an evidence path that is missing or a directory, and --flat-output into a folder that already holds packages/ or manifest.json.

What a run writes

  • The run folder comes from partitioned_run_dir; readers such as the validators and the Realizer's fleet run resolve the newest one under a root (latest_run_dir, latest_publisher_run_dir).
  • Each package is schema-validated, then written with sorted keys; then the evidence, the workbook and the manifest (package_locked_contract).
  • The manifest records the Publisher and contract versions, the run scope and warehouse selection, one entry per package, excluded warehouses, the live-only check for billed warehouses with no configuration snapshot, and the names of the workbook and evidence files (build_manifest).
  • The Realizer's layout, state directory and per-warehouse lock are in resolve_layout.
Sensitive output

evidence.json and the Realizer's measurement files hold real identities, owner emails and tags. Keep them out of git and out of shared channels; send packages, manifests and workbooks only as agreed.

The workbook

The workbook is a projection of the packages for people who read spreadsheets. It has exactly four visible sheets, Executive Summary, Warehouse Portfolio, Scenario Plans, Recommendation Registry, with no formulas, macros or hidden sheets. It never recalculates a recommendation, a confidence, an ID or an economic figure: every cell is copied from a package field. Annual impact is numeric and signed (positive is a saving, negative a cost increase) beside explicit currency and impact-type columns, and unavailable economics stay unavailable rather than zero.

The first live run

The sequence, its commands and its starter prompts live in the live run sequence. Phase 1 uses the golden miner skill to compare real warehouses with the golden scenarios; phase 4 measures one applied change weekly for four weeks with the Realizer. In the fleet runs of phase 4 the collector warehouse shows as SKIPPED in the manifest, because it cannot measure itself.

Phase 3 replays one saved evidence.json under all three cost profiles. The comparison is of decisions, not of package IDs or estimates: the same change has the same estimate under every profile, so what differs is which cuts ship, how deep a target a looser profile picks, and which small savings pass the materiality floor. Checkpoint B also carries the nonprod tag check: the tag keys and values across the fleet against the lists that select the aggressive default, with any change proposed as a decision (cost profile calibration).

Check yourself
Why does the run timestamp appear only in the folder name and never inside a file?

So that replaying the same evidence writes byte-identical files. Determinism is checked by comparing outputs, and a timestamp inside a file would make every run differ.

Why must the live collector warehouse never be the warehouse being measured?

The collector's own queries would add running time and queries to the measured warehouse and distort the very usage being measured. The Realizer's live access check refuses that pairing.

A teammate asks for a workbook column showing combined savings across all candidates. Where would that logic go?

Nowhere in Excel. The workbook only projects package fields. Candidate savings are non-additive, so the figure would be wrong anyway; the combined figure is the recommended scenario's stateful estimate, which the package already carries.

Why does the Realizer keep its ledger in a state directory separate from its run folders?

The ledger is the history of each realization and must survive every run; run folders are per-run projections. Keeping one state directory means a weekly scheduler appends to one history instead of forking it.

Glossary

Terms underlined with a dotted line throughout the guide show these definitions on hover or keyboard focus. Each links to the document that owns the term.

Attribution
Whether a realized saving can be claimed for the recommendation. CLAIMABLE needs every financial-quality gate to pass and no hard disqualifier. ledger-contract.md
AWS cost
The EC2 cost of a Pro or Classic warehouse, modeled from running cluster time and the on-demand price registry. Serverless has no separate AWS cost. aws-cost-model.md
Billed cross-check
The Realizer compares the replayed saving with the drop in billed DBU cost, scaled for volume, and calls it AGREES, DISAGREES or INCONCLUSIVE against the week-to-week noise. source-evidence-contract.md
Blocker code
An upper-case reason code on a candidate or scenario that explains why a change is held, needs a test, is unavailable or was rolled back. blocker-codes.md
Canary
A change applied as a test and judged on its own new-epoch evidence before it is trusted - a size change, a lower minimum or a type migration. A tripped fail-fast guard rolls it back on the next run. context.md
Canary rollback
When a fail-fast guard trips on the new epoch's evidence after a canary-type change, the Publisher recommends restoring the previous value (ACTIONABLE, no savings claimed) and holds conflicting cuts. blocker-codes.md
Candidate
One decision for one knob (CAND- ID) with its status, blockers, evidence references and isolated economics. Candidate savings are not additive and must never be summed. reporter-json-contract.md
Cluster-minute
One cluster running for one minute - the unit auto-stop, min-cluster and replay math work in before pricing. lld.md
Confidence
A deterministic 0 to 1 score from evidence coverage, sample, cost stability, epoch maturity and signal, capped by status. HIGH at or above 0.80, MEDIUM at or above 0.60. lld.md
Configuration epoch
A span of time during which a warehouse kept one configuration (type, size, min and max clusters, auto-stop, channel). The current epoch drives every recommendation; older epochs feed calibration, backtests and three narrow exceptions. context.md
Cost profile
Aggressive, balanced or conservative. It changes only the risk-appetite thresholds of cuts (which cuts ship, how deep a few targets go, the materiality floor), never evidence floors, product constants, estimator or confidence parameters, or the rules that add capacity. The same change has the same estimate under every profile (the one exception is the Pro target of a Serverless-to-Pro migration, priced within the profile's cold-start budget). thresholds.md
Counterfactual
What the old configuration would have cost over the measured window - for auto-stop, a replay of the observed running and idle time under the old value. context.md
Current epoch
The configuration in force now. Recommendations, their targets and their economics come only from its evidence; running time, idle time, cluster-minutes and billing never carry over from an older epoch. context.md
DBU
Databricks Unit, the billing unit for SQL warehouse compute. DBU cost and AWS infrastructure cost are always kept as separate components. aws-cost-model.md
Determinism
Identical normalized evidence, cost profile and versions produce identical decisions, IDs, confidence and economics, byte for byte. context.md
Evidence registry
The package's evidence map - each EVID- record is defined once and referenced by ID from candidates and scenarios. reporter-json-contract.md
Execution state
Where a plan step stands - READY, READY_FOR_CANARY, REQUIRED (a validation or re-measure step), PENDING_REEVALUATION, BLOCKED or INVALIDATED. reporter-json-contract.md
Fail closed
When support is unknown the product refuses rather than guesses - for example, warehouse types outside CLASSIC, PRO and standard SERVERLESS are never routed into existing algorithms. context.md
Fail-fast guard
A rule that fails a change when a metric is both above its safe level and worse than before by more than a margin - failures, cold starts, queueing, spill or p95 latency. policy-contract.md
Forward baseline
The no-change cost of the next 365 days, forecast from the current epoch's settled billing (a blended 28/84-day run rate with a damped trend, or a cadence model for periodic workloads). lld.md
Golden case
A committed scenario with its input evidence and the exact expected output. Any behavior change shows up as a golden diff that must be approved. golden-scenarios.md
Human in the loop (HITL)
Every change is approved and applied by a person. The products are read-only and never call a mutation API. prd.md
Implementation conformance
How the applied change matches the recommendation - EXACT (the recommended value), MODIFIED (a different value in the same direction), NOT_APPLIED, CONTRARY or UNRELATED. ledger-contract.md
Knob
One tunable warehouse setting the product may recommend a change to - size, max clusters, min clusters, auto-stop or warehouse type. Photon and the channel are observed but never recommended. technique-catalog.md
Lineage
The chain of packages for one warehouse over time. Only one lineage can own a given applied change; any other gets CLAIMED_BY_OTHER_LINEAGE. ledger-contract.md
Low, base, high
The three tracks of every modeled range - conservative, base and optimistic realization. They are scenario bounds, not a probability interval. Unknown values are null, never zero. reporter-json-contract.md
Materiality floor
The smallest annual saving worth a change (cost_change_min_annual_savings, set by the cost profile). A cost change below it is held by the value gate, and a plan step whose marginal saving falls below it is held too. thresholds.md
Maturity
How much post-change history backs a realization - NOT_APPLIED, COLLECTING, PROVISIONAL, REPRESENTATIVE, then MATURE at 365 covered days. ledger-contract.md
Non-additive
Candidate savings are each priced in isolation against the same baseline, so adding them double-counts. Only the stateful scenario estimate combines steps. reporter-json-contract.md
Package envelope
Package economics - low is the minimum scenario low, base is the recommended scenario's base, high is the maximum scenario high. An envelope over alternatives, not a sum and not a probability interval. reporter-json-contract.md
Product constant
A documented Databricks limit or behavior the rules rely on, such as the auto-stop floor or the max-cluster limit. Platform facts, not policy, so no profile changes them. product-constants.md
Realization
What an applied change actually saved, measured by the Realizer against a counterfactual of the old configuration over the same window. context.md
Realization ledger
An append-only JSON Lines file per RPKG. Every fact the Realizer learns is an event; the realization package is a projection of it. ledger-contract.md
Realization package (RPKG)
The Realizer's current view of one PKG - application, validation, economics, attribution, maturity - projected from the ledger. ledger-contract.md
Recognition status
Whether a measured saving is booked - CONFIRMED when the counterfactual is claim-eligible and the measurement is not provisional, PROVISIONAL otherwise, REJECTED when a guardrail failed. ledger-contract.md
Recommendation status
The decision on a candidate - ACTIONABLE (apply with human approval), TEST_REQUIRED (canary first), NO_CHANGE, INSUFFICIENT_EVIDENCE, BLOCKED or REVIEW. reporter-json-contract.md
RecommendationPackage
The Publisher's public output for one warehouse and its current epoch (PKG- ID). It is the machine source of truth; the workbook only projects it. reporter-json-contract.md
Replay evidence
evidence.json, the versioned envelope a run writes and --from-evidence reads back, reproducing the same packages offline. It holds owner emails and tags, so it is sensitive. evidence-format.md
Run scope
The --scope, --scope-file or --warehouse restriction of what a run recommends. It never restricts what is observed or decided; the package records it in run_scope. lld.md
Running idle gap
A stretch of RUNNING time with no query executing. A lower auto-stop removes the part of each gap beyond the new value, at the price of extra restarts. lld.md
Safety inclusion
A candidate kept in a package outside its run scope because it is a safety action - a canary rollback after a tripped fail-fast guard. The package lists it in run_scope.safety_inclusions. reporter-json-contract.md
Scenario
An ordered, mutually exclusive execution path (SCN- ID) built from candidates - optimize the current type in place, or migrate the warehouse type. One scenario is RECOMMENDED, the others are ALTERNATIVE. reporter-json-contract.md
Stateful bundle estimator
Prices a scenario step by step, each step acting on the cost and resource state the previous steps left, on three tracks (low, base, high). lld.md
Technique
The algorithm that decides one knob, with a stable ID such as WH-AUTOSTOP-REDUCE-001. Each technique emits exactly one candidate per package. technique-catalog.md
Thresholds
The frozen dataclass holding every policy, evidence, confidence and estimator default. A change to it is decision-affecting and bumps versions. thresholds.md
Value gate
A cost change ships only if its own modeled savings are positive and at least the materiality floor (cost_change_min_annual_savings); otherwise it is held with the modeled economics still visible. lld.md

How this guide is built and refreshed

This page is generated by the teach-me skill in .claude/skills/teach-me/. Its facts (versions, thresholds, constants, flags, tables, the worked example) are imported from the code and the reference documents each time it is built; its narrative comes from chapter fragments that cite the code they explain. Do not edit the HTML: change a fragment or the generator and rebuild.

/teach-me

Builds the guide if it is missing; otherwise reports whether it is current and offers a refresh. /teach-me <topic> answers a question in chat from the matching chapter without rebuilding.

/teach-me refresh

Finds the chapters whose cited source files changed, re-reads that code, rewrites only those chapters, rebuilds and verifies.

python .claude/skills/teach-me/scripts/build_guide.py --stale    # chapters whose cited sources changed
python .claude/skills/teach-me/scripts/build_guide.py --verify   # rebuild, then check citations, examples, links
