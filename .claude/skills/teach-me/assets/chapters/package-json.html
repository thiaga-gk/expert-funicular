The {{term:package}} is the Publisher's only public answer: one JSON document per warehouse and current epoch, schema-validated, content-addressed and frozen. Everything else, the workbook included, is a projection of it. Learn to read it and you can audit any recommendation without running the code.

The top-level blocks

The schema requires {{fact:schema.package_required|count}} top-level fields. Three of them may be null (observed_change, carried_forward_plan, run_scope); every other field is always present, so a consumer never has to guess whether an absent key means zero, unknown or not applicable. Grouped by the question they answer:

Which warehouse, which epoch

recommendation_package_id, contract_version, warehouse (with current_epoch), current_config.

What we know

workload_profile, cost_baseline, assessment, evidence, observed_change.

What we recommend

candidates, scenarios, recommended_plan, package_economics.

Under which policy

cost_profile, run_scope, provenance (every component version and the hashes).

After the change

realization, always NOT_APPLIED with no records when published; the Realizer keeps its own records.

Reserved

carried_forward_plan, always null in current producers.

Scenarios, steps and the recommended plan

A {{term:scenario}} is an ordered, mutually exclusive path. Plan A optimizes the current warehouse type in place; Plan B migrates the type. They are alternatives, so the owner follows one. Each scenario holds an execution_plan of steps. A step has a step_type (CANDIDATE, COMPATIBILITY_VALIDATION, REMEASURE) and an {{term:execution-state}}:

  • {{status:READY}}: an ACTIONABLE change a person can apply now, like the auto-stop step.
  • {{status:READY_FOR_CANARY}}: a TEST_REQUIRED change applied as a {{term:canary}} and judged on the new epoch's own evidence, like the size step.
  • {{status:REQUIRED}}: a gate that is not a knob change: validate migration compatibility first, or re-measure and regenerate after a step that invalidates other knobs.
{{explorer:pkg|scenarios[status=RECOMMENDED]|2}}

recommended_plan names the chosen scenario (scenario_id), why it was chosen (selection_reason_code: here {{pkg:recommended_plan.selection_reason_code}}), what to do next ({{pkg:recommended_plan.next_action}}) and whether a person must approve (requires_hitl = {{pkg:recommended_plan.requires_hitl|json}}; always true, because the products never apply anything). Economics fields and their meaning

Every money figure in the package follows the same rules ({{doc:docs/contracts/shared/reporter-json-contract.md#15-package_economics|contract section 15}}):

  • DBU and AWS are separate components with a total; Serverless has no AWS component of its own. Unknown is null with an availability or estimation status, never zero.
  • Ranges have three tracks, {{term:low-base-high}}. They are scenario bounds from conservative to optimistic realization, not a confidence interval.
  • Savings are signed: positive saves money, negative costs money. A low track can be negative, as the size step's is in the example.
  • Candidate economics are isolated and non-additive; scenario economics are stateful (each step acts on the state the previous one left); package economics are an {{term:envelope}} over scenarios.

IDs and the package hash

Every public ID is content-addressed: a prefix plus the first {{fact:hash_hex_length}} uppercase hex characters of a SHA-256 over an explicit payload ({{cite:src/publisher/contracts/reporter_contract.py::content_id}}). Identical evidence, cost profile and versions therefore give identical IDs on every machine, and any change to an input gives a new ID.

The package hash covers the decision, not the presentation. Its payload holds the contract and component versions, the warehouse and epoch, the canonical configuration, an evidence fingerprint ({{cite:src/publisher/contracts/reporter_contract.py::make_evidence_fingerprint}}), the ordered candidate and scenario IDs, the re-evaluation, the observed-change and carried-forward fingerprints, the cost profile and the run scope. generated_at, prose and file names never enter it, so re-running the same evidence a day later yields the same ID.

Canonical rules ({{cite:src/publisher/contracts/reporter_contract.py::canonicalize_for_hash|canonicalize_for_hash}}): keys sorted, numbers turned into normalized decimal strings so 1 and 1.0 hash the same, list order kept because callers decide which lists are ordered (set-like lists are sorted before they enter the payload), null kept, NaN refused. The Realizer recomputes this hash before it accepts a package, so a hand-edited package is rejected.

Write order

The order is fixed so the ID and hash always describe exactly the bytes that are validated and written.

  1. {{cite:src/publisher/packager/packager.py::_build_locked_recommendation_package}} assembles the frozen dataclass with a placeholder ID, replaces it with {{cite:src/publisher/contracts/reporter_contract.py::expected_package_id|expected_package_id()}}, stores {{cite:src/publisher/contracts/reporter_contract.py::full_package_hash|full_package_hash()}} in provenance, and runs the semantic validate().
  2. The Reviewer's package gate ({{cite:src/publisher/reviewer/package.py::review_contract}}) runs validate() again, checks that cost_profile.applied_thresholds match the profile's name, and validates against the committed schema {{cite:schema/recommendation-package.schema.json}}.
  3. The Reporter ({{cite:src/publisher/reporter/json_reporter.py::package_locked_contract}}) validates the serialized payload against the schema once more and writes json.dumps(payload, indent=2, sort_keys=True) to packages/<workspace_id>__<warehouse_id>.json, then evidence.json, the workbook and manifest.json.

Read a package in five minutes

  1. recommended_plan: the chosen scenario, the next action and the decision summary.
  2. That scenario's execution_plan, in step order: what changes, in which execution state, and where a canary or re-measure gate sits.
  3. Each candidate's status and blockers, including the NO_CHANGE ones; open evidence_refs when a decision surprises you.
  4. package_economics: low, base and high, the currency, and the excluded scenarios. Do not sum candidate savings.
  5. cost_baseline.forward_365d: the no-change cost the savings are measured against, and which components are available.
  6. assessment: overall_status and evidence_quality tell you how much to trust the rest.
  7. cost_profile, run_scope and observed_change: the risk appetite, the scope, and whether the configuration just changed.
  8. provenance: when comparing two packages, check the component versions first; a version change explains a decision change.

The full field reference is the {{doc:docs/contracts/shared/reporter-json-contract.md|Reporter JSON Contract}}; the semantic rules the schema cannot express are in its section 18.

Check yourself
Two runs over the same evidence, one with --scope current and one unscoped, produce different PKG- IDs. Is that a bug?

No. run_scope is part of the package hash payload, so the restricted package gets its own ID. The in-scope candidates keep the same CAND- IDs, because scope is not a candidate hash input.

Why is generated_at not part of the package hash?

It is volatile presentation metadata. Excluding it lets a replay of the same evidence reproduce the same ID and the same bytes, which is what makes golden tests and the Realizer's hash check possible.

A candidate's savings_365d.total is null. What does that mean, and what must a consumer not do?

The saving could not be priced (for example a missing price or too little cost history); the estimation status and blockers say why. A consumer must not treat it as zero or drop it from a total as if it were zero.

The package envelope's low and high both name Plan A. How can that be when Plan B has a higher base?

The envelope takes the lowest low and highest high across scenarios and the base of the recommended one. Plan B's whole range sits inside Plan A's, so both bounds come from Plan A, and the base comes from Plan A because it is recommended.
