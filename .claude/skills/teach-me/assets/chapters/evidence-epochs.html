Every decision starts from evidence the collector reads out of Databricks system tables and normalizes into one {{cite:src/publisher/contracts/source.py::WarehouseEvidence}} per (workspace_id, warehouse_id). The evidence is cut into {{term:epoch|configuration epochs}}, because a metric only describes the configuration it was measured under. Getting the epoch right is what keeps a recommendation from being judged on the wrong configuration.

Where the facts come from

The collector ({{cite:src/publisher/analyzer/collector/collector.py::extract_evidence}}) runs each read-only query once over the whole fleet and assembles the rows. It is the only place raw rows become typed evidence, and it logs counts and IDs only: never SQL text, owner emails, tags or configuration values.

Configuration epochs

system.compute.warehouses writes a snapshot whenever any property changes, including the name or tags. The epoch query folds cosmetic snapshots into the surrounding period and starts a new epoch only when a decision field changes: type, channel, size, min clusters, max clusters or auto-stop. Renaming a warehouse therefore never resets its history. The {{term:current-epoch|current epoch}} is the open one; its ID enters every candidate, scenario and package hash.

The three exceptions to "current epoch only"

Older epochs are calibration and backtest material. They never choose a change, its target or its economics, with three narrow exceptions.

1 · Older peak holds a cut

If an older epoch of the same warehouse within the last 365 days reached more clusters of peak demand than the recent window, capacity cuts wait (OLDER_EPOCH_PEAK_DEMAND_HIGHER). Each older epoch's sustained peak (the level held for {{fact:thresholds.peak_demand_min_minutes}} busy minutes) is compared with the recent peak in clusters at {{fact:product_constants.QUERIES_PER_CLUSTER_PRO_CLASSIC}} queries per cluster. Computed in {{cite:src/publisher/analyzer/findings.py::Analyzer}}.

2 · Evidence a change cannot affect

A change to auto-stop or cluster limits does not change how heavy each query is. So when the current epoch is younger than the 30-day query window, demand and per-query evidence is read back to the last size, type or channel change, and capacity queueing back to the last change of size, type, channel, min or max clusters ({{cite:src/publisher/analyzer/collector/queries/query_history.py::PERIODS_CTE}}). The fields that carry are listed in {{cite:src/publisher/analyzer/epochs.py::DEMAND_CARRY_FIELDS}} and {{cite:src/publisher/analyzer/epochs.py::QUEUE_CARRY_FIELDS}}; {{cite:src/publisher/analyzer/epochs.py::carried_query_view}} lays them over the current epoch's.

3 · Canary rollback

After a canary-type change (one size down or a lower minimum), {{cite:src/publisher/analyzer/findings.py::canary_observation}} compares the current epoch with the one immediately before it. A tripped fail-fast guard makes the Optimizer recommend restoring the previous epoch's value ({{term:canary-rollback}}).

Never carried

Running time, idle time, cluster-minutes and billing always come from the current epoch alone. They are what a configuration change actually changes, so mixing in an older epoch would price the new configuration with the old one's behavior. Cold-start wait also never carries, because auto-stop changes it.

Settled billing and readiness

Billing arrives late and is sometimes corrected. A UTC day counts only {{fact:thresholds.billing_settle_hours}} hours after it ends and once the account's billing watermark has passed it ({{cite:src/publisher/analyzer/collector/billing.py::billing_check_through}}). When a warehouse simply stopped running, its workspace watermark stalls at the last usage; {{cite:src/publisher/analyzer/collector/billing.py::effective_billing_watermark}} uses warehouse events to tell "no usage" from "usage not ingested yet", and keeps the workspace watermark when it cannot tell. --billing-ingested-through pins billing to what was ingested by a date, so a re-collection reproduces an earlier run.

Before any size, cluster or auto-stop change is decided, the current configuration needs {{fact:thresholds.readiness_min_billed_days}} settled billed days ({{cite:src/publisher/analyzer/epochs.py::ready_billed_days}}). Readiness counts billed days rather than calendar age, so a warehouse that rarely runs is not judged on days it did nothing. Epoch age itself is computed from the analysis time, never the wall clock ({{cite:src/publisher/analyzer/epochs.py::epoch_age_days}}).

evidence.json and replay

Every run writes the normalized evidence it decided on to evidence.json (a live run writes it twice, the second time with the same bytes: first right after extraction, so a later refusal or crash still leaves a replayable file, then with the finished run): a versioned envelope with evidence_format_version {{fact:versions.publisher.evidence_format_version}}, the Publisher version and the list of warehouses ({{cite:src/publisher/analyzer/collector/replay.py::save_evidence}}). It is validated against schema/evidence.schema.json before it is written and again when --from-evidence loads it ({{cite:src/publisher/analyzer/collector/replay.py::validate_evidence_payload}}). Any other version, or a bare list, is rejected; there are no legacy shims.

publisher --from-evidence ./demo_out/evidence.json --output-dir ./replay_out

A replay needs a readable evidence file: a missing path, a directory or an unreadable file is a refusal (exit status 2) that names the file, not a traceback, and a run is either replayed or simulated, so --demo with --from-evidence is refused as well ({{cite:src/publisher/analyzer/collector/replay.py::load_evidence_files}}).

Because decisions are deterministic, a replay of the same evidence under the same versions produces byte-identical packages. That makes the file the unit of reproduction for bug reports and the input of the golden cases.

Sensitive file

evidence.json holds owner emails and warehouse tags. Validation errors name the failing path and rule, never the value, and the loader logs counts and IDs only. Treat the file like any other export containing personal data.

Check yourself
An owner renames a warehouse. Does it get a new epoch?

No. Only decision fields (type, channel, size, min and max clusters, auto-stop) start an epoch; name and tag snapshots fold into the surrounding period, so history and readiness are kept.

Auto-stop changed nine days ago. Which period does the p95 execution time come from?

From the last size, type or channel change, clipped to the 30-day query window: auto-stop cannot change how long a query runs, so that evidence carries across the change. Idle time and billing still come from the nine-day current epoch only.

Can an older, busier epoch make the Publisher recommend more clusters?

No. An older peak can only hold a capacity cut. Older epochs never choose a change, its target or its economics.

Why is readiness counted in billed days and not calendar days?

A warehouse that runs twice a week would otherwise look "ready" after days of no activity. Settled billed days count only days the configuration actually ran and was billed.
