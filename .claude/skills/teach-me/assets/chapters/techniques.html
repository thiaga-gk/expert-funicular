The Optimizer turns the Analyzer's facts into exactly one decision per {{term:knob}}. Each decision is a pure function of the current epoch's evidence and the {{term:thresholds}} of the warehouse's {{term:cost-profile}}: no wall clock, no randomness, no guesses. A missing fact never reads as "no pressure"; it becomes a {{term:blocker}} code and the change waits.

One decision per knob, in a fixed order

{{cite:src/publisher/optimizer/optimizer.py::Optimizer|Optimizer.optimize}} calls the techniques in the order size, max clusters, min clusters, auto-stop, migration, and each appends exactly one decision. The order matters once: the migration technique reads the auto-stop decision, because a warehouse that runs with no queries needs a human review before any migration experiment. One decision per knob holds by construction, which is the invariant the candidate gate checks.

Every technique first asks whether the configuration is ready. A decision is "young" when the current {{term:epoch}} has fewer than {{fact:thresholds.readiness_min_billed_days}} settled billed days (readiness_min_billed_days); young evidence holds a change with CURRENT_CONFIG_EPOCH_TOO_NEW. The thresholds themselves come from {{cite:src/publisher/governor/cost_profiles.py::thresholds_for_profile}}, so an aggressive or conservative profile only moves the risk-appetite levels of cuts.

After the techniques run, {{cite:src/publisher/optimizer/optimizer.py::in_scope}} keeps the knobs in the {{term:run-scope}} and always keeps a canary rollback, since a rollback is a safety action.

{{status:ACTIONABLE}}

Apply with human approval. The evidence is direct enough that no test is needed (a lower auto-stop, a max-cluster change, a rollback).

{{status:TEST_REQUIRED}}

A {{term:canary}}: the effect is modeled, not observed, so the change is applied as a test and judged on its new epoch (size, a lower floor, a migration, a higher auto-stop).

{{status:NO_CHANGE}}

The current value stays. Blocker codes say what held a change, or the list is empty when today's value is already right.

{{status:INSUFFICIENT_EVIDENCE}}

The evidence a rule needs is missing, thin or too young. Nothing is priced.

{{status:BLOCKED}}

A change is warranted but a hard limit or guard refuses it (largest size, max-cluster limit, failures).

{{status:REVIEW}}

A person must decide first, for example whether a warehouse that ran with no queries is still needed.

Warehouse size

{{cite:src/publisher/optimizer/techniques/size.py::decide|size.decide}} looks for spill first. Spill must be both frequent (at least {{fact:thresholds.spill_query_pct_upsize}}% of queries, spill_query_pct_upsize) and severe (a p95 of spilled bytes among the spilled queries at or above spill_p95_bytes_upsize), backed by at least {{fact:thresholds.severity_min_affected_queries}} spilled queries. Frequency without a reported severity is INSUFFICIENT_EVIDENCE. When {{fact:thresholds.spill_concentration_hold_pct}}% or more of the spilled bytes come from the top {{fact:thresholds.spill_concentration_top_sources}} statement sources, the fix is a rewrite of those statements, so the size stays (SPILL_CONCENTRATED_IN_FEW_STATEMENTS).

Without an upsize signal the technique tries one size down, and every safety signal can veto it: spill above spill_query_pct_downsize_safe, queueing above queue_query_pct_safe, failures above failure_cancel_pct_downsize_safe, p95 and p99 latency limits, fewer than {{fact:thresholds.strong_query_sample_size}} executed queries, growing query volume, a peak in the current epoch above the recent window, or an older epoch that peaked higher. A batch warehouse (job queries at least {{fact:thresholds.batch_job_query_share_pct}}% of the load) is judged on {{fact:thresholds.batch_min_active_days}} run days instead of the query sample and the latency limits.

Why a resize is never ACTIONABLE

The speed-up or slowdown of a resize and its cost are modeled, never observed. A resize also invalidates the max- and min-cluster decisions, which were measured at the old size, so they wait for a re-measurement.

Max clusters

{{cite:src/publisher/optimizer/techniques/scaling.py::decide_max_clusters}} raises the ceiling only when three signals agree: queued queries at or above {{fact:thresholds.queue_query_pct_increase_max}}%, a capacity-wait p95 at or above queue_wait_p95_ms_increase_max, and time at the ceiling at or above {{fact:thresholds.time_at_max_pct_saturated}}% (time_at_max_pct_saturated). For Pro and Classic the target comes from demand in one move:

Pro/Classic ceiling target{{cite:src/publisher/optimizer/techniques/scaling.py::decide_max_clusters|scaling.py}}
required = ceil( Pmax_cluster_target_percentile(running + queued queries per busy minute) / QUERIES_PER_CLUSTER_PRO_CLASSIC ) target = min( MAX_CLUSTERS_SUPPORTED_LIMIT, max( min_clusters, required + max_cluster_target_headroom_clusters ) )
percentile = {{fact:thresholds.max_cluster_target_percentile}} queries per cluster = {{fact:product_constants.QUERIES_PER_CLUSTER_PRO_CLASSIC}} limit = {{fact:product_constants.MAX_CLUSTERS_SUPPORTED_LIMIT}} headroom = {{fact:thresholds.max_cluster_target_headroom_clusters}}
Serverless scales differently, so its increase is one cluster at a time, and its confidence is capped by confidence_cap_serverless_ceiling_increase ({{fact:thresholds.confidence_cap_serverless_ceiling_increase}}).

A decrease needs an unused ceiling: time at the ceiling at or below time_at_max_pct_safe_reduce, low queueing, a mature epoch and no evidence blockers. The new ceiling never drops below the recent window's observed peak, and the whole current epoch's peak holds the cut when it is higher than what the recent window shows (PEAK_OUTSIDE_RECENT_WINDOW), so a quarter-end peak is not cut away. The cut is ACTIONABLE with objective COST_GUARDRAIL: a lower ceiling caps runaway cost, but on a warehouse that never reaches it, it saves nothing directly.

Min clusters

{{cite:src/publisher/optimizer/techniques/scaling.py::decide_min_clusters}} sizes the floor by what it actually does: it carries the first minutes of a busy period until the autoscaler adds clusters. The target is the smallest floor that covers the busy-start demand at the min_cluster_busy_start_percentile percentile ({{fact:thresholds.min_cluster_busy_start_percentile}}). It needs at least {{fact:thresholds.min_cluster_min_busy_periods}} busy periods, and it is held when the warehouse sits at its ceiling a lot (time_at_max_pct_block_min_reduce) or rarely at its floor (time_at_min_pct_reduce). Every proposal carries SPARE_FLOOR_CAPACITY_UNPROVEN because its saving is an upper bound the canary measures.

Auto-stop

The Analyzer scores every value on the type's grid against the warehouse's measured {{term:idle-gap|running idle gaps}} in {{cite:src/publisher/analyzer/findings.py::_auto_stop_options}}; {{cite:src/publisher/optimizer/techniques/autostop.py::decide|autostop.decide}} then chooses.

Net saving of one auto-stop value{{cite:src/publisher/analyzer/findings.py::_auto_stop_options|findings.py}}
lower value: net = removable running cluster-minutes − additional starts × restart_cost higher value: net = avoided starts × restart_cost − added idle cluster-minutes restart_cost = restart_cost_cluster_minutes_pro_classic (or _serverless) × floor clusters
restart cost per start: Pro/Classic {{fact:thresholds.restart_cost_cluster_minutes_pro_classic}} cluster-minutes, Serverless {{fact:thresholds.restart_cost_cluster_minutes_serverless}} cold-start budget: added starts ≤ {{fact:thresholds.cold_start_added_share_max_pct}}% of queries (none for Serverless) near-best band: within {{fact:thresholds.auto_stop_near_best_pct}}% of the best net saving, then the smallest change from today
A gap counts as removable only inside RUNNING time, so idle that the warehouse never paid for is never "saved". Choosing the smallest change inside the near-best band keeps the move conservative when several values save about the same.

A lower value is {{status:ACTIONABLE}}: its saving rests on observed idle time. A higher value saves only restarts, and whether starting minutes are billed is an assumption, so it is {{status:TEST_REQUIRED}} with RESTART_BILLING_UNVERIFIED. A Serverless warehouse set below the console's lowest value through the API is left alone. Activity that keeps a warehouse running with no query (open sessions, keep-alive) is flagged on every outcome and never priced.

Warehouse-type migration

{{cite:src/publisher/optimizer/techniques/migration.py::decide|migration.decide}} proposes Serverless to PRO or Pro/Classic to SERVERLESS as a {{status:TEST_REQUIRED}} canary, priced with a pre-canary DBU and AWS counterfactual (see the estimation chapter). It invalidates all four other knobs, because every one of them was measured on the old type. When system tables have not shown the target type in the workspace, the decision carries a capability blocker such as SERVERLESS_WORKSPACE_CAPABILITY_NOT_CONFIRMED_FROM_SYSTEM_TABLES. Unsupported types never get here: the Analyzer {{term:fail-closed|fails closed}} on them.

Canary rollback and conflicts

After a canary-type change (one size down or a lower minimum), {{cite:src/publisher/analyzer/findings.py::canary_observation}} compares the new epoch with the one just before it, for at most 30 days after the change. A guard trips only when a metric is both above its safe level and more than {{fact:thresholds.canary_p95_regression_pct}}% (canary_p95_regression_pct) worse than before, with a minimum sample: failures, queueing, spill after a downsize, or p95 execution time on statement sources seen in both epochs (at least {{fact:thresholds.canary_p95_min_queries}} queries).

When a guard trips, {{cite:src/publisher/optimizer/conflicts.py::apply_canary_rollback}} rewrites the decisions in place:

  • The changed knob becomes an {{status:ACTIONABLE}} PERFORMANCE decision that restores the previous epoch's value, with CANARY_GUARDRAIL_BREACHED plus the tripped guard codes. No saving is claimed. This is the only place an older epoch's configuration sets a decision.
  • Cuts that conflict with the restore become {{status:NO_CHANGE}} with CANARY_ROLLBACK_PENDING: after a size rollback, lower cluster values; after a floor rollback, a lower ceiling or a smaller size. An increase for queueing or spill is never held.
  • The planner puts the rollback first in every plan, and every run scope keeps it.

The value gate

A decision says what should change; the candidate estimator then prices it, and {{cite:src/publisher/optimizer/estimator/candidate.py::Estimator|Estimator._value_gate}} holds a cost change that does not pay for itself. The held candidate keeps its modeled economics, so the reason stays visible.

Cost changes

A change made to save money (objective COST) is held when its own base savings are not positive (COST_CHANGE_NOT_COST_EFFECTIVE) or below {{fact:thresholds.cost_change_min_annual_savings}} a year (cost_change_min_annual_savings, COST_SAVINGS_BELOW_MATERIALITY). An ACTIONABLE cost change with no price waits for its price; an unpriced canary is not gated, because the canary will measure it.

Migrations

A migration is held only when even its best case, the high end of total savings, is not positive (MIGRATION_NOT_COST_EFFECTIVE). Total only: Serverless DBUs include compute that Pro and Classic pay as AWS, so DBU alone is not comparable across types.

Observed, never recommended

Photon and the warehouse channel appear in current_config but no technique changes them. Photon's state is inferred from current-epoch billing (product_features.is_photon) by {{cite:src/publisher/analyzer/normalizer.py::infer_photon_observation}}; Databricks publishes no Photon on/off price for SQL warehouses, so any saving would be a guess. A channel move has no priced effect. Their technique IDs are reserved and never emitted.

Check yourself
A warehouse shows no spill, no queueing and fast queries. Why might the size still be NO_CHANGE?

Absence of pressure is necessary, not sufficient. The downsize also needs a strong query sample (or enough batch run days), a ready epoch, no growth, no failure spike, and no peak in the current or an older epoch that the recent window does not show. Missing evidence for any signal is itself a blocker.

Why is lowering auto-stop ACTIONABLE while raising it is TEST_REQUIRED?

A lower value saves observed idle time inside RUNNING segments. A higher value only saves restarts, and the restart cost assumes starting minutes are billed, which is not documented, so the billed cost must be measured after the change (RESTART_BILLING_UNVERIFIED).

The run scope is current:auto-stop, yet the package contains a size rollback. Is that a bug?

No. Every knob is decided first and the scope filters afterwards, but in_scope() always keeps a decision carrying CANARY_GUARDRAIL_BREACHED: a rollback is a safety action.

A max-cluster cut is ACTIONABLE. How much does it save?

Nothing is claimed. A cut is a COST_GUARDRAIL: it never drops below the observed peak, so it removes no running time; it limits what a runaway workload could cost.
