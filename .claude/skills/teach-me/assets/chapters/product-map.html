inframate-v1 is two read-only products around one hand-off file. The Publisher reads Databricks system tables and writes one locked {{term:package}} per SQL warehouse, saying which configuration change would save money and how sure it is. A person reviews the package and applies a change by hand. The Realizer then takes that package, watches the warehouse after the change and records in an append-only ledger what was actually saved.

Two products, one contract

Publisher {{fact:versions.publisher.publisher_version}}

Answers "what should change on this warehouse, why, and what is it worth?" Entry point {{cite:src/publisher/publisher.py::publish}}. Writes one package per warehouse under packages/, plus evidence.json, workbook.xlsx and manifest.json.

Realizer {{fact:versions.realizer.realizer_version}}

Answers "the owner applied it; what did it actually save, and can we claim it?" Entry point {{cite:src/realizer/realizer.py::realize_request}}. One PKG in, one {{term:rpkg|RPKG}} and one {{term:ledger|ledger}} out.

The hand-off is the Reporter JSON Contract {{fact:versions.reporter_contract}}. The Realizer accepts exactly the contract version it was built for ({{fact:versions.realizer_formats.supported_publisher_contract}}), checks the package against the Publisher's schema and recomputes its PKG- ID before it reads anything else. Invariants that shape every layer

These rules come from the product requirements and the domain model. When a design question comes up, they usually settle it.

Deterministic

Identical normalized evidence, cost profile and versions produce identical decisions, IDs, confidence and economics, byte for byte. Nothing reads the wall clock or randomness during a decision; the analysis time is an input. See {{term:determinism}}.

Read-only

OAuth profiles only; a static personal access token is rejected. There is no mutation API and no apply step. The only HTTP verb in the shared access layer is GET ({{cite:src/workflow_shared/databricks/access.py::api_get}}). See {{term:hitl}}.

Fail closed on warehouse types

Only {{fact:supported_warehouse_types|list}} are analyzed. An unknown or future type is excluded with a reason code, never routed into an existing algorithm ({{cite:src/publisher/analyzer/analyzer.py::_is_supported_warehouse}}). See {{term:fail-closed}}.

Unknown is null, never zero

Unpriced usage, missing AWS prices or thin history leave a cost null with a status code. A zero would read as "free" and inflate savings. {{term:dbu|DBU}} and {{term:aws-cost|AWS}} costs always stay separate components.

One candidate per knob

Every package decides each active {{term:knob|knob}} exactly once: {{fact:active_knobs|list}}. Photon and the warehouse channel are observed and reported, never recommended, because neither has a priced effect.

The JSON is the truth

The package is the machine source of truth. The workbook ({{fact:workbook.sheet_names|list}}) only projects it: no formula, estimate, ID or selection logic lives in Excel.

Check yourself
Who changes the warehouse configuration?

A person. Both products are read-only: no mutation API, no apply step. The Publisher proposes, the owner applies by hand, the Realizer observes the result in system tables.

A billing row has no list price. What cost does the package show?

null with an unavailability status, never 0. A zero would make the usage look free and overstate savings; unknown stays visible as unknown.

Why does the Realizer recompute the package ID before reading the package?

The ID is a content hash. Recomputing it proves the file is exactly what the Publisher produced, so the Realizer measures against the real recommendation and not an edited copy.

Photon is enabled on a warehouse. Will the Publisher recommend turning it off?

No. Photon is inferred from billing and reported in current_config.photon, but Databricks publishes no Photon on/off price for SQL warehouses, so any savings figure would be a guess.
