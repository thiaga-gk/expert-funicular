This chapter is the operator's view: the commands that run each product in each mode, the folders a run writes, the workbook, the first live run on a real account, and the checks that keep a change honest. Both products only read the account; the one change in any workflow is the one an owner makes by hand.

Command recipes

Each product has one console script in front of a facade: the CLI parses and validates its own arguments, builds a request and calls the facade once. A refused input (an unknown scope name, a package that fails its hash check, a static token) exits with status {{cite:src/publisher/cli/main.py::EXIT_REFUSED|2}} and a one-line message. A Realizer fleet run returns 1 if any warehouse crashed, else 2 if any was refused, else 0 ({{cite:src/realizer/cli/realize.py::run_fleet}}).

Publisher Demo and replay

# one simulated warehouse per golden scenario
publisher --demo --output-dir ./demo_out
python scripts/run_demo.py ./demo_out          # same run, no install

# replay a run's evidence offline, restricted to one technique and warehouse
publisher --from-evidence ./out/run_date=.../run_ts=.../evidence.json \
  --scope current:auto-stop --warehouse wh-demo-001 --output-dir ./out

# scope from a file, cost profile for some warehouses
publisher --demo --scope-file examples/scopes/current-auto-stop.json --output-dir ./demo_out
publisher --demo --cost-profile conservative --cost-profile aggressive=wh-demo-001 --output-dir ./demo_out

Publisher Live, read-only

databricks auth login --host https://<workspace> --profile WHOPT   # OAuth; static tokens are rejected
publisher \
  --profile WHOPT \
  --sql-warehouse-id <collector-warehouse> \
  --source-region us-east-1 \
  --output-dir ./out
# reproduce an earlier collection despite later billing corrections
publisher ... --billing-ingested-through 2026-10-01

The collector warehouse runs the read-only SQL. Pro and Classic AWS cost needs --source-region in the price registry; --allow-missing-aws-price publishes with that cost unavailable.

What a run writes

  • The run folder comes from {{cite:src/publisher/config/output_layout.py::partitioned_run_dir}}; readers such as the validators and the Realizer's fleet run resolve the newest one under a root ({{cite:src/publisher/config/output_layout.py::latest_run_dir}}, {{cite:src/realizer/config/output_layout.py::latest_publisher_run_dir}}).
  • Each package is schema-validated, then written with sorted keys; then the evidence, the workbook and the manifest ({{cite:src/publisher/reporter/json_reporter.py::package_locked_contract}}).
  • The manifest records the Publisher and contract versions, the run scope and warehouse selection, one entry per package, excluded warehouses, the live-only check for billed warehouses with no configuration snapshot, and the names of the workbook and evidence files ({{cite:src/publisher/packager/manifest.py::build_manifest}}).
  • The Realizer's layout, state directory and per-warehouse lock are in {{cite:src/realizer/config/output_layout.py::resolve_layout}}.
Sensitive output

evidence.json and the Realizer's measurement files hold real identities, owner emails and tags. Keep them out of git and out of shared channels; send packages, manifests and workbooks only as agreed.

The workbook

The workbook is a projection of the packages for people who read spreadsheets. It has exactly four visible sheets, {{fact:workbook.sheet_names|list}}, with no formulas, macros or hidden sheets. It never recalculates a recommendation, a confidence, an ID or an economic figure: every cell is copied from a package field. Annual impact is numeric and signed (positive is a saving, negative a cost increase) beside explicit currency and impact-type columns, and unavailable economics stay unavailable rather than zero.

Column order and groups live only in {{cite:src/publisher/contracts/workbook_contract.py::SHEET_NAMES|workbook_contract.py}}; the renderer {{cite:src/publisher/reporter/workbook_reporter.py::write_workbook}} consumes them and keeps no second list. Check a run with python scripts/validate_workbook.py ./demo_out. The Realizer writes its own three-sheet realization workbook in a fleet run.

The first live run

The sequence, its commands and its starter prompts live in {{doc:docs/proposals/shared/live-run.md|the live run sequence}}. Phase 1 uses the golden miner skill to compare real warehouses with the golden scenarios; phase 4 measures one applied change weekly for four weeks with the Realizer.

Change loop, goldens and versions

A change is small and layer-local, then checked from the bottom up:

  1. Compile check, then every test: python -m compileall -q src tests scripts examples and python -m unittest discover -s tests -v.
  2. Regenerate the demo and validate the workbook. Packages are validated as they are written, so a failed validation aborts the demo.
  3. A decision-affecting change bumps the affected component versions in {{cite:src/publisher/config/versions.py::PUBLISHER_VERSION|versions.py}} and regenerates the goldens and the contract example in the same commit.
  4. A new threshold, product constant or blocker code gets its row in the reference documents; tests/test_docs.py fails otherwise.
  5. The documents that describe the changed behavior change in the same commit, and this guide is refreshed with /teach-me refresh.
python scripts/update_goldens.py --case <name> --approved-change "<why>"     # Publisher goldens
python scripts/update_realizer_e2e_goldens.py --check                         # Publisher-to-Realizer drift
python scripts/compare_with_ref.py --ref master                               # output diff against a git ref
python scripts/compare_realizer_with_ref.py --ref master
python scripts/validate_contracts.py                                          # the contract example

Check yourself
Why does the run timestamp appear only in the folder name and never inside a file?

So that replaying the same evidence writes byte-identical files. Determinism is checked by comparing outputs, and a timestamp inside a file would make every run differ.

Why must the live collector warehouse never be the warehouse being measured?

The collector's own queries would add running time and queries to the measured warehouse and distort the very usage being measured. The Realizer's live access check refuses that pairing.

A teammate asks for a workbook column showing combined savings across all candidates. Where would that logic go?

Nowhere in Excel. The workbook only projects package fields. Candidate savings are non-additive, so the figure would be wrong anyway; the combined figure is the recommended scenario's stateful estimate, which the package already carries.

Why does the Realizer keep its ledger in a state directory separate from its run folders?

The ledger is the history of each realization and must survive every run; run folders are per-run projections. Keeping one state directory means a weekly scheduler appends to one history instead of forking it.
