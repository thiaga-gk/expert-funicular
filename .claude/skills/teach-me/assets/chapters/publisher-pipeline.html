A Publisher run is seven capabilities called once each, in a fixed order, by a facade that holds no domain logic. Each capability answers one question and hands an immutable result to the next: the Analyzer observes, the Governor decides what may be considered, the Optimizer decides and prices isolated changes, the Packager plans and prices scenarios and assembles the package, the Reviewer verifies twice, and the Reporter writes files.

The facade and the context

{{cite:src/publisher/publisher.py::publish}} only sequences calls. It first calls {{cite:src/publisher/publisher.py::build_context}}, which validates the execution mode, parses the --cost-profile flags and resolves the run scope through the config layer ({{cite:src/publisher/config/loader.py::resolve_scope}}), so a bad flag is refused before any evidence is read. The result is a {{cite:src/publisher/contracts/request.py::RunContext}} holding the request, a fresh {{term:thresholds|Thresholds}} and the scope.

Two in-memory entry points run the same capabilities on evidence already in hand and write nothing: {{cite:src/publisher/publisher.py::evaluate_warehouses}} stops after the scenario gate, {{cite:src/publisher/publisher.py::build_recommendation_packages}} returns reviewed packages. Tests and the golden harness use them.

What each capability decides, and what it never decides

Analyzer

{{cite:src/publisher/analyzer/analyzer.py::run}} collects evidence (demo, replay or live), then {{cite:src/publisher/analyzer/analyzer.py::analyze}} computes findings per knob for every supported warehouse under its {{term:cost-profile|cost profile}}. Unsupported types keep their evidence but get no findings.

Never decides eligibility, a recommendation or economics.

Governor

{{cite:src/publisher/governor/governor.py::govern}} narrows the fleet to the run scope's warehouses, records a fail-closed exclusion for each unsupported one and passes the scope on. A live run also stops here when the source region has no AWS price, unless the request allows publishing with AWS cost unavailable.

Never observes and never recommends.

Optimizer

{{cite:src/publisher/optimizer/optimizer.py::Optimizer}} runs the five techniques in a fixed order, then the canary rollback; {{cite:src/publisher/optimizer/optimizer.py::in_scope}} drops out-of-scope decisions afterwards (a rollback always stays), and the candidate estimator prices each survivor in isolation.

Never combines candidates; their savings are {{term:non-additive|non-additive}}.

Packager

{{cite:src/publisher/packager/packager.py::plan}} builds the scenarios and prices them with the stateful bundle estimator; {{cite:src/publisher/packager/packager.py::assemble}} turns each warehouse into one frozen {{term:package}}.

Never changes a candidate's decision.

Reviewer

A fail-fast invariant gate ({{cite:src/publisher/reviewer/reviewer.py::Reviewer}}). It raises on the first violated rule and changes no decision, ID or economics. A rejection aborts the run.

Never repairs.

Reporter

{{cite:src/publisher/reporter/reporter.py::run}} writes what it was given and counts it. Nothing is recalculated.

Never reads its outputs back into a decision.

The order inside the Optimizer matters: migration reads the auto-stop decision, and the rollback rewrites decisions already made. Every knob is decided before the scope filter runs, so cross-technique holds are the same in every scope. Chapter Techniques has the rules.

The two Reviewer gates

The candidate gate ({{cite:src/publisher/reviewer/reviewer.py::review_candidates}}) checks each warehouse's candidates: one per in-scope knob, identity and epoch consistency, configuration limits, cost and confidence rules. The package gate ({{cite:src/publisher/reviewer/reviewer.py::review_package}}) first re-runs the scenario checks ({{cite:src/publisher/reviewer/reviewer.py::review_plans}}), then {{cite:src/publisher/reviewer/package.py::review_contract}}: the package's semantic validate(), a check that the published cost profile carries exactly the thresholds its name applies, and the committed Draft 2020-12 JSON Schema ({{cite:src/publisher/reviewer/package.py::validate_locked_package_schema}}).

Gate logging

A rejection logs the warehouse identity and a short rule label only. Gate messages and schema errors can embed values, so the full text never reaches the log.

Package write order

A package's ID is a hash of its content, so the order of operations is fixed and every step depends on the one before.

  1. Assemble

    {{cite:src/publisher/packager/packager.py::_build_locked_recommendation_package}} builds the frozen package with a placeholder PKG-000… ID.

  2. Set the ID, then the full hash

    The ID becomes expected_package_id(); then provenance.package_hash_full_sha256 gets the full SHA-256 of the same hash payload. Volatile metadata such as generated_at is not in the payload.

  3. Semantic validation

    package.validate() checks cross-field rules the schema cannot express.

  4. Schema validation

    The package gate validates against the committed schema; the Reporter validates again just before writing.

  5. Serialize and write

    {{cite:src/publisher/reporter/json_reporter.py::package_locked_contract}} writes packages/<workspace>__<warehouse>.json with sorted keys, then evidence.json, workbook.xlsx (unless disabled) and manifest.json.

A failed validation raises before the file is written, so a run never leaves a package on disk that does not match its own hash or the schema.

Boundaries enforced by tests

The CLI is an adapter

{{cite:src/publisher/cli/publish.py::run}} parses its own flags, creates the run folder and log, builds the {{cite:src/publisher/contracts/request.py::PublisherRequest}} and calls publish. It never imports a capability package; {{cite:tests/unit/publisher/cli/test_cli.py}} checks this. {{cite:src/publisher/cli/main.py::main}} maps a PublisherError to exit status {{cite:src/publisher/cli/main.py::EXIT_REFUSED|2}} and re-raises anything else as a bug.

Shared access is neutral

OAuth, GET-only REST and the UTC-pinned SQL client live in src/workflow_shared/, which imports neither product (tests/unit/workflow_shared/test_boundaries.py). The Publisher passes its identity in {{cite:src/publisher/analyzer/collector/workspace_api.py::PUBLISHER_ACCESS}}.

Check yourself
Where would you add a rule that holds a size cut when spill is high?

In the size technique inside the Optimizer (optimizer/techniques/size.py), reading a fact the Analyzer computes. The Analyzer observes, the Governor gates eligibility, the Optimizer decides; mixing them breaks the layering.

The candidate gate finds two candidates for the same knob. What happens?

It raises, the run aborts and nothing is written for that run. Gates verify and never repair, so a broken invariant is a bug to fix, not a case to patch over.

Why can't the PKG- ID be set before the package is complete?

The ID is a hash of the package's identity payload (versions, epoch, configuration, evidence fingerprint, ordered candidate and scenario IDs and more). It can only be computed once those are final; the full hash comes from the same payload.

A run is scoped to auto-stop only. Does the Optimizer still decide size?

Yes. Every knob is decided first so cross-technique holds behave the same in every scope; the scope filter then drops the out-of-scope decisions. A canary rollback is kept in every scope.
