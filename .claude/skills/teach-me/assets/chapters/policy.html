Policy is the set of numbers that decides how much evidence is enough and how much risk a cut may take. It lives in one frozen object, {{cite:src/publisher/governor/thresholds.py::Thresholds}}, owned by the Governor. Cost profiles adjust a small part of it per warehouse, and a run scope limits what gets recommended. Databricks platform facts sit beside the policy and are never adjusted.

Thresholds: one frozen policy object

Thresholds is a frozen dataclass with {{fact:threshold_count}} fields: evidence floors (how many queries, how many settled billed days), pressure limits (queueing, spill, latency), estimator parameters (forecast weights, realization factors), confidence weights and caps, and planner risks. The Governor owns it; every technique and estimator receives the instance it should use instead of reading globals. Its __post_init__ refuses confidence weights that do not sum to one, and derived caps such as confidence_cap_default are properties computed from the cut-offs, so a cap can never drift above the level it is meant to keep a candidate below.

A change to any default changes decisions. The repo treats it like a code change to an algorithm: bump the affected component versions in {{cite:src/publisher/config/versions.py}}, regenerate the golden cases, and update the row in {{doc:docs/reference/publisher/thresholds.md#parameter-reference|thresholds.md}}. A test compares that document's defaults with the dataclass, so the two cannot drift.

Rule

Prose names a parameter; only the dataclass and its reference page hold the number. When you need a value in code, read it from the Thresholds instance you were given. A literal such as 500 in a technique would escape both the cost profile and the version bump.

Cost profiles

Every warehouse is evaluated under exactly one {{term:cost-profile}}: conservative, balanced or aggressive. Balanced is the dataclass defaults. The other two replace only the fields named in {{cite:src/publisher/contracts/reporter_contract.py::COST_PROFILE_GROUPS}}, grouped by technique, with the values in {{cite:src/publisher/governor/cost_profiles.py::_OVERLAYS}}. {{cite:src/publisher/governor/cost_profiles.py::thresholds_for_profile}} returns the base instance for balanced and a dataclasses.replace copy otherwise, so every field outside the groups is identical under all three profiles.

may change

How much measured pressure a cut may tolerate (spill, p95 and p99 latency, queueing, time at the floor or ceiling), the added cold-start share a lower auto-stop may cause, the canary rollback margin, the growth hold, and the materiality floor of the value gate (cost_change_min_annual_savings).

never changes

Evidence minimums, product constants, forecast and estimator parameters, confidence, classification rules, the failure and cancel guard, and every rule that adds capacity (size up, max-cluster increase). A candidate's price is therefore the same under every profile; only whether a cut is allowed moves.

How a warehouse gets its profile ({{cite:src/publisher/governor/cost_profiles.py::assign_cost_profiles}}), first match wins:

  1. A per-warehouse flag, --cost-profile aggressive=wh-demo-005 (a bare warehouse ID, or workspace_id/warehouse_id when the ID exists in several workspaces). A reference that names no collected warehouse stops the run instead of silently falling back.
  2. An all-warehouse flag, --cost-profile conservative.
  3. The tag default: a current-epoch tag whose key is in nonprod_tag_keys ({{fact:thresholds.nonprod_tag_keys|list}}) and whose value is in nonprod_tag_values selects aggressive ({{cite:src/publisher/governor/cost_profiles.py::nonprod_tag_match}}).
  4. Otherwise balanced.

Flags are parsed by the config layer ({{cite:src/publisher/config/cost_profiles.py::parse_cost_profile_flags}}), which rejects an unknown profile or one warehouse given two different profiles.

The package records the choice in cost_profile: the name, the source (CLI_WAREHOUSE, CLI_ALL, TAG_DEFAULT or DEFAULT), the source detail and the effective applied_thresholds ({{cite:src/publisher/governor/cost_profiles.py::applied_thresholds}}). Under conservative the same floor would be {{fact:profiles.conservative.cost_change_min_annual_savings|money}}, under aggressive {{fact:profiles.aggressive.cost_change_min_annual_savings|money}}.

Why the profile is hashed

The profile name and its applied thresholds are inputs to the candidate, scenario and package IDs. The same evidence evaluated under two profiles produces different IDs even when every decision happens to match, so a package always states which risk appetite produced it. The package gate re-derives applied_thresholds from the name and refuses a package whose values disagree ({{cite:src/publisher/reviewer/package.py::review_contract}}).

Product constants are not policy

Some numbers describe Databricks itself: how long a Pro or Classic warehouse waits before adding a cluster, the lowest auto-stop each type accepts, the cluster limits, how many concurrent queries one cluster serves. They live in {{cite:src/publisher/config/defaults.py::PRODUCT_CONSTANTS}} with a source link per row in {{doc:docs/reference/publisher/product-constants.md|product-constants.md}}. No profile or policy version changes them; when Databricks changes a limit, the constant and its documented source change together.

Two examples of how they bound decisions: the auto-stop technique never evaluates a value below {{fact:product_constants.AUTO_STOP_FLOOR_PRO_CLASSIC}} minutes on Pro or Classic ({{fact:product_constants.AUTO_STOP_FLOOR_SERVERLESS}} on Serverless), and a max-cluster increase stops at {{fact:product_constants.MAX_CLUSTERS_SUPPORTED_LIMIT}}.

Run scope

A {{term:run-scope}} restricts what a run recommends. It never restricts what is observed or decided. The config layer ({{cite:src/publisher/config/loader.py::resolve_scope}}) turns --scope, --scope-file and --warehouse into a frozen {{cite:src/publisher/contracts/scope.py::RunScope}}: the knobs in scope and the selected warehouses. No input gives the full scope, which reproduces an unscoped run. The scenario and technique names come from {{cite:src/publisher/config/defaults.py::SCOPE_SCENARIOS}}:

{{table:scope}}
  • Analyzer: collects and normalizes every visible warehouse, so evidence.json can be replayed under any scope.
  • Governor: the warehouse selection narrows the eligible fleet ({{cite:src/publisher/governor/eligibility.py::selected_warehouse_keys}}). A selector that matches nothing, or a bare ID found in two workspaces, stops the run.
  • Optimizer: every knob is decided first; {{cite:src/publisher/optimizer/optimizer.py::in_scope}} then keeps the in-scope decisions plus any decision carrying CANARY_GUARDRAIL_BREACHED. A rollback is a safety action and survives every scope.
  • Packager: builds the in-place plan when current is in scope or a rollback must run, and the migration plan when migration is in scope. Without an in-place plan the recommended scenario is a step-less NO_CHANGE_BASELINE, so a migration experiment is never the recommended path.
  • Package: a restricted scope is written to run_scope with the scoped knobs per scenario type and the safety_inclusions (rollbacks published outside the scope) ({{cite:src/publisher/packager/packager.py::_run_scope_contract}}). It is null for a full assessment, as in the example (run_scope = {{pkg:run_scope|json}}).
# only the auto-stop technique of the in-place scenario, every warehouse
publisher --demo --output-dir ./demo_out --scope current:auto-stop

# two in-place techniques, one warehouse
publisher --demo --output-dir ./demo_out --scope current:auto-stop,min-clusters --warehouse wh-demo-005

# the same choices from a file (it holds the warehouse list too, so it is not combined with --scope or --warehouse)
publisher --demo --output-dir ./demo_out --scope-file examples/scopes/current-auto-stop.json

Scope files follow {{cite:schema/run-scope.schema.json}}, generated from SCOPE_SCENARIOS by {{cite:src/publisher/contracts/scope.py::build_scope_schema}}: every scenario and technique toggle is required and unknown keys are rejected. Ready-made examples live in {{cite:examples/scopes/}}. The full semantics per capability are in {{doc:docs/architecture/publisher/lld.md#54-run-scope|LLD section 5.4}}.

Same candidate in every scope

Scope is not a candidate hash input and candidates are priced alone against the current configuration. An in-scope candidate is therefore byte-identical to the same candidate in a full run of the same evidence; only the package ID changes, because run_scope is part of the package hash.

Eligibility and the supported-type gate

The Governor decides what the Optimizer may consider ({{cite:src/publisher/governor/governor.py::govern}}). Its one hard rule is {{term:fail-closed}}: only {{fact:supported_warehouse_types|list}} (standard Serverless) are analyzed ({{cite:src/publisher/config/defaults.py::SUPPORTED_WAREHOUSE_TYPES}}, checked by {{cite:src/publisher/analyzer/analyzer.py::_is_supported_warehouse}}). Any other or future type is never routed into the existing algorithms. It is listed once with reason UNSUPPORTED_WAREHOUSE_TYPE ({{cite:src/publisher/governor/eligibility.py::unsupported_warehouse_exclusions}}) and recorded in the run manifest, while the rest of the fleet is still evaluated.

A live run also checks the AWS price registry before anything is decided ({{cite:src/publisher/governor/constraints.py::aws_region_price_guard}}). When the source region is missing from the registry, the run stops unless --allow-missing-aws-price is given, in which case Pro and Classic AWS cost is published as unavailable rather than guessed. Demo and replay runs skip this check.

Check yourself
A warehouse is tagged env=dev and the run passes --cost-profile conservative. Which profile applies?

Conservative. An all-warehouse flag beats the tag default; only a per-warehouse flag would beat that flag. The package's cost_profile.source reads CLI_ALL.

Can switching to the aggressive profile raise a candidate's estimated savings?

No. Profiles never touch estimator or forecast parameters, so a candidate's economics are the same under every profile. Aggressive can only let a cut through that a stricter profile holds, or let a smaller saving pass the materiality floor.

A run is scoped to migration, but the size canary from last week tripped its p95 guard. What does the package contain?

The migration candidate, plus the size rollback listed in run_scope.safety_inclusions. The rollback is kept because in_scope never drops a decision carrying CANARY_GUARDRAIL_BREACHED, and the recommended scenario becomes an in-place scenario holding only that rollback.

Why is the auto-stop floor in PRODUCT_CONSTANTS and not in Thresholds?

It is a documented Databricks limit, not a risk choice. Keeping it out of Thresholds means no cost profile and no policy version can push a recommendation below what the platform accepts.
