The Realizer answers one question for one package: after an owner applied a recommended change, how much did it actually save? It reads one locked RecommendationPackage and an observation of the warehouse after the change, prices what the old configuration would have cost over the same days (the {{term:counterfactual}}), and appends what it learns to an append-only {{term:ledger}}. Like the Publisher it is read-only and deterministic: it never changes a warehouse and never edits the package.

One line of math, many gates

Realized saving = counterfactual old cost − observed new cost. Everything else in this chapter decides whether that number is trustworthy: may it be measured yet, was the change really the recommended one, did performance hold, is the counterfactual defensible, and may the saving be claimed for the recommendation.

The pipeline

{{cite:src/realizer/realizer.py::realize_request}} calls each capability once, in order, and holds no domain logic, the same shape as the Publisher's publish(). Inputs are checked before anything is written ({{cite:src/realizer/realizer.py::build_context}}), then the run holds the lock of its ledger until the Reporter has written. The first thing recorded is the lineage entry (REALIZATION_CREATED), so even a run that fails later leaves a ledger that says the package exists.

Analyzer

Turns the observation source into one normalized observation: plans the measurement windows (settled whole weeks after the change and the same span before it), runs the counterfactual for the changed knob and gathers guard metrics. The only module that runs Publisher SQL is {{cite:src/realizer/analyzer/collector/bridge.py|bridge.py}}.

Governor

Pure policy checks held lazily: readiness, the fail-fast guards, counterfactual eligibility and the financial-quality gates, all from {{cite:src/realizer/governor/policy.py::RealizerPolicy}} and the package's own cost-profile thresholds.

Reconciler

Matches what the warehouse runs to the published plan (exact, modified, independent change), decides lifecycle events (application, drift, rollback, supersession, regeneration) and resolves ownership across the warehouse's lineages. It prices nothing.

Estimator, Reviewer, Packager, Reporter

The Estimator computes realized economics and attribution ({{cite:src/realizer/estimator/economics.py::calculate_economics}}, {{cite:src/realizer/estimator/attribution.py::attribution_result}}). The Reviewer assembles the validation episode and the recognition status and cannot reject anything. The Packager appends ledger entries and projects the snapshot; the Reporter writes the files.

What it accepts from the Publisher

{{cite:src/realizer/config/loader.py::validate_package}} refuses any package that is not an unmodified Publisher package of the supported contract, before a single file is written. The checks run in this order:

  1. contract_version equals exactly {{fact:versions.realizer_formats.supported_publisher_contract}} ({{cite:src/realizer/config/loader.py::SUPPORTED_PUBLISHER_CONTRACT}}). There is no range: a new Publisher contract needs a Realizer release.
  2. The package passes the Publisher's committed JSON Schema.
  3. The PKG- id and provenance.package_hash_full_sha256, recomputed from the hashed fields, match. A hand-edited package fails here.
  4. The realization block is the Publisher's empty NOT_APPLIED placeholder. The Realizer's own record is the RPKG, never this block.
  5. carried_forward_plan is null, the recommended scenario exists, the warehouse type is one of {{fact:supported_warehouse_types|list}}, and no plan step recommends its current value.

From an accepted package it reads the warehouse identity, current_config, the recommended scenario and its execution plan (step, knob, current and recommended value, execution state, dependencies, invalidations, running savings), each candidate's independent_economics, the evidence, cost_profile.applied_thresholds, run_scope, observed_change and the package currency. For the worked example the RPKG id follows directly: {{ex:realizer.rpkg_id|id}} from {{pkg:recommendation_package_id|id}}.

Where the observation comes from

One observation source per run. Every mode ends in the same normalized observation, so the pipeline above never knows which one it got.

--demo

A simulated world for a Publisher demo-fleet warehouse: its first eligible step is applied a week after the package and measured four settled weeks later. --demo-modified applies a size step one size off, to exercise the modified path.

Live

--profile (OAuth only) with --sql-warehouse-id naming a collector warehouse. The run refuses a collector that is the warehouse being measured, because its own queries would pollute the measurement.

--from-evidence

Replays the measurement evidence file a live or demo run wrote under realization/measurements/, offline and byte-identical.

--observation

A ready-made normalized observation file, for tests and caller-supplied measurements.

--publisher-run

A fleet run over every warehouse of a Publisher run folder, one at a time, each failure isolated to its warehouse, then a run manifest and the realization workbook.

--backtest

Past auto-stop changes from system tables, with no package and no ledger: it checks the replay method against changes that already happened.

Counterfactuals per knob

A counterfactual prices the actual post-change days under the old value, holding every other knob at its observed value. That is why a workload change does not fake a saving: busier days cost more under both values.

Auto-stop: replay claim-eligible

The collector measures, for the post-change running time, how many idle cluster-minutes the old value would have added and how many restarts it would have avoided. Raising back to the old value costs added_idle − avoided_starts × restart_cost; replaying a lower value is the negative of removable − additional_starts × restart_cost. The restart cost is the package's assumption per start times max(1, min_clusters). {{cite:src/realizer/analyzer/projector.py::replay_net_cluster_minutes}}

Size: runtime ratio claim-eligible

ρ is the post-change queries' execution time at post-change medians over the same queries at pre-change medians, per statement source seen in both windows. The old size's running minutes have two bounds from the observed R1: elastic R1 × (1 − b + b/ρ) and inelastic R1; the claim takes the smaller saving. The old size's measured price must sit within the published rate band. {{cite:src/realizer/analyzer/size_counterfactual.py::counterfactual_running}}

Min clusters: floor levels claim-eligible

From running minutes per cluster count: the counterfactual runs every level at least at the old floor, Σ minutes × max(n, old_floor), against the observed Σ minutes × n. A floor raise is never measured: minutes at the new, higher floor cannot say what the old floor would have run. {{cite:src/realizer/analyzer/cluster_counterfactual.py::floor_cluster_minutes}}

Max clusters no saving

A capacity add is a cost, priced as the cluster-minutes above the old cap and judged on performance. A cap cut yields only an upper bound of what the old cap could have added. {{cite:src/realizer/analyzer/cluster_counterfactual.py::above_cap_cluster_minutes}}

Migration observed only

There is no reverse model of what the old type would have billed for the new type's days, so the Realizer reports the bill's movement against the pre-change window carried forward (method CORRELATED_ONLY) and claims nothing (NO_REVERSE_MIGRATION_MODEL). {{cite:src/realizer/analyzer/migration_observation.py::migration_delta}}

Only {{cite:src/realizer/contracts/observation.py::CLAIM_ELIGIBLE_COUNTERFACTUAL_METHODS}}. The auto-stop replay records itself as CALIBRATED_PRIOR_STATE: the prior state's behaviour replayed on the observed days.

Fail-fast guards and readiness

A saving only counts if performance held. {{cite:src/realizer/governor/policy.py::validate_performance}} applies the Publisher's own canary guard with the package's cost-profile limits. Each rule is PASS, FAIL or UNKNOWN; one FAIL fails validation, and an UNKNOWN means "not ready yet", never "failed".

The two-part rule{{cite:src/realizer/governor/policy.py::_two_part|policy.py}}
FAIL when post > safe level AND post > pre × (1 + margin%) with the minimum sample
REAL-FAIL-001 failure/cancel share safe {{fact:thresholds.failure_cancel_pct_downsize_safe}}%, margin {{fact:thresholds.canary_p95_regression_pct}}% (every knob) REAL-COLD-001 added cold-start share budget {{fact:thresholds.cold_start_added_share_max_pct}}% (auto-stop; Serverless has no budget) REAL-QUEUE-001 queued share safe {{fact:thresholds.queue_query_pct_safe}}% (other knobs) REAL-SPILL-001 spilled share safe {{fact:thresholds.spill_query_pct_downsize_safe}}% (size) REAL-P95-001 p95 on shared sources rise above {{fact:thresholds.canary_p95_regression_pct}}% (other knobs)
Both parts matter: a metric that was already high before the change is not blamed on it, and a large relative rise from a tiny base is not a failure while it stays under the safe level. The Realizer policy can only tighten the p95 limit, never loosen it. These are the balanced defaults; the package's cost profile supplies the values actually applied.

Readiness ({{cite:src/realizer/governor/policy.py::readiness}}) needs a minimum number of days and queries, a representative regime, sufficient evidence quality and no guard without evidence. A step that was a canary (READY_FOR_CANARY) stays provisional for the Publisher's guard window ({{cite:src/realizer/config/settings.py::CANARY_GUARD_WINDOW_DAYS}}).

Classifying the result

The checks run in a fixed order, and the first that applies decides. The order encodes priorities: a failed guard beats everything, an indefensible counterfactual is blocked before any comparison, and a currency or workload shift is reported but never judged against an expectation priced under other conditions.

The comparable volume band is the post-over-pre query ratio {{cite:src/realizer/config/settings.py::VOLUME_RATIO_BAND}} ({{fact:realizer.volume_ratio_band[0]}} to {{fact:realizer.volume_ratio_band[1]}}); the example's ratio is {{ex:realizer.volume_ratio}}. The ratio thresholds of step 8 are policy fields of {{cite:src/realizer/governor/policy.py::RealizerPolicy}}.

Which expectation is the denominator

{{cite:src/realizer/estimator/economics.py::denominator}} picks the expected annual savings to compare with:

  • One step applied exactly: that candidate's independent_economics.savings_365d (PUBLISHER_CANDIDATE). This is the example.
  • Several plan steps applied in order: the last applied step's projected_economics.running_savings_365d, the stateful scenario value (PUBLISHER_SCENARIO).
  • A modified auto-stop (the owner chose a different value): the package's own option grid re-prices the applied value by linear interpolation (REESTIMATED_APPLIED_SCOPE, method PACKAGE_OPTION_GRID).
  • A migration: the scenario's pre-canary range, informational only.

Attribution: may the saving be claimed?

Measuring a saving and claiming it for the recommendation are separate decisions. {{cite:src/realizer/estimator/attribution.py::attribution_result}} collects hard disqualifiers; with none, a qualified origin and passing financial-quality gates, the claim is {{status:CLAIMABLE}} with {{status:HIGH_CONFIDENCE}}. Otherwise it is OBSERVABLE_ONLY (validated, but partially or only correlated) or NOT_ATTRIBUTABLE.

Financial-quality gates

Attributable spend at least {{rpkg:attribution.economic_quality_gates.attributable_spend.required_min_pct}}%, price coverage {{rpkg:attribution.economic_quality_gates.price_coverage.required_min_pct}}%, currency consistency {{rpkg:attribution.economic_quality_gates.currency_consistency.required_pct}}% and equal to the package's, a complete correction chain and the material cost components available. A gate whose input is null does not pass. {{cite:src/realizer/governor/policy.py::economic_quality_result}}

Hard disqualifiers

Applied state unmatched, guardrail failed, no defensible counterfactual (or no reverse migration model), overlap with another scope, an independent change not held constant, canary window still open, billed cross-check disagrees, origin independent or not attributable, a performance or capacity step, or the change is owned by another lineage.

Origin

CONFIRMED when an approvals file names this package, the knob and the observed value; INFERRED when the knob changed after the package was generated; otherwise UNKNOWN, which cannot support the strict claim. The example is {{rpkg:attribution.origin_attribution}}. {{cite:src/realizer/analyzer/projector.py::origin}}

One owner per change

A warehouse can have several packages over time (lineages). Only one can own a given applied change; the others get CLAIMED_BY_OTHER_LINEAGE. {{cite:src/realizer/reconciler/lineage.py::ownership}}

Recognition is a third, separate status ({{cite:src/realizer/reviewer/economics.py::recognition_status}}): REJECTED when a guardrail failed, CONFIRMED when the counterfactual is eligible and not provisional, PROVISIONAL otherwise. The example's attributed realized saving for the period is {{rpkg:attribution.recommendation_attributed_realized_savings|money}}.

The billed cross-check

The replay is a model. The cross-check asks whether the bill agrees: it scales the pre-change billed cost per day by the volume ratio to the post-change days and compares the drop with the replayed DBU saving, against the week-to-week noise of the pre-change bill. It is the only statistical test in the Realizer.

Billed reduction against noise{{cite:src/realizer/analyzer/crosscheck.py::billed_cross_check|crosscheck.py}}
billed reduction = pre cost / pre days × volume ratio × post days − post cost noise = pstdev(pre weekly costs) × √(post days / 7) INCONCLUSIVE when |replay| < {{fact:realizer.noise_multiple}} × noise, another knob changed, volume shifted or billing is incomplete AGREES when the signs match and |billed − replay| ≤ {{fact:realizer.agreement_band_pct}}% of |replay|, else DISAGREES
pre weekly costs = {{ex:realizer.weekly}} noise = {{ex:realizer.noise}} replay DBU saving {{ex:realizer.replay_dbu}} is far above {{fact:realizer.noise_multiple}} × noise billed reduction = {{ex:realizer.billed_reduction}} difference = {{ex:realizer.diff_pct}}% → {{ex:realizer.cross_check}} ✓
A DISAGREES outcome is a hard disqualifier: a person looks at it before anything is claimed. The {{fact:realizer.noise_multiple}}× noise multiple and the {{fact:realizer.agreement_band_pct}}% agreement band are constants in {{cite:src/realizer/analyzer/crosscheck.py::AGREEMENT_BAND|crosscheck.py}}.

Maturity, realized to date and corrections

Daily runs measure overlapping windows. {{cite:src/realizer/packager/to_date.py::realized_to_date}} gives each instant the value of the latest measurement covering it, pro rata, and sums the covered instants; a re-measured window replaces the earlier value for its days. Maturity follows the evidence ({{cite:src/realizer/packager/snapshot.py::project_snapshot}}):

  • {{status:NOT_APPLIED}} no application observed; COLLECTING applied, nothing measured yet; {{status:PROVISIONAL}} measured but not ready.
  • {{status:REPRESENTATIVE}} measured with readiness passed, as in the example ({{rpkg:economics.realized_to_date.days_covered}} days covered).
  • {{status:MATURE}} once measurements cover {{cite:src/realizer/packager/to_date.py::MATURE_DAYS}} ({{fact:realizer.mature_days}}) days; the trailing-twelve-month figure then fills mature_ttm_realized_savings.

Billing is restated sometimes. When a later run measures an already-measured window with different billing, the new measurement is recorded with a correction entry that points back at the one it replaces ({{cite:src/realizer/estimator/economics.py::correction_facts}}). Nothing is overwritten. The Realizer also never performs a rollback: "rollback" means it recorded a requested or observed return to the old value, or a later package that undid the change.

Check yourself
Why does the auto-stop replay run on the post-change days instead of comparing the month before with the month after?

A before-and-after bill comparison mixes the change with everything else that moved: more queries, different days. Replaying the old value on the observed post-change days holds the workload fixed, so the difference is the change alone. The before-and-after view survives only as the billed cross-check.

The example's annualized saving is above the published high. Why is it still plain REALIZED?

The replay measures the full mechanical effect, which is the optimistic track behind the published high. Only a result above {{fact:realizer.review_above_high}} × high is flagged for review (REVIEW_ABOVE_HIGH). Anything at or above the low counts as realized.

A measurement passes every guard, but the query volume doubled after the change. What happens?

The saving is still measured, because the counterfactual prices the actual post-change days. It is classified MONITORING with WORKLOAD_SHIFT, never realized or under-realized, because the package's expectation was priced at the old workload. The cross-check also turns INCONCLUSIVE.

Why can a warehouse migration never be CLAIMABLE?

There is no model of what the old type would have billed on the new type's days. The observed delta uses the pre-change window carried forward (CORRELATED_ONLY), so anything else that moved the bill is inside it. The attribution carries NO_REVERSE_MIGRATION_MODEL and the claim stays observable only.
