The Realizer writes three kinds of JSON: an append-only ledger that is the history of one package's realization, a realization package (RPKG) that projects that history into a current view, and the measurement evidence a live or demo run collected, so the same measurement can be replayed offline. This chapter walks each one with the real files of the worked example.

Where the files live

Two roots. The state directory outlives runs and holds every warehouse's history. Each run also writes a fresh run folder with that run's projections. Reading the ledger again always reproduces the projections, so the history in the state directory is what you back up. {{cite:src/realizer/config/output_layout.py::resolve_layout}}

A fleet run also writes a run manifest (format {{fact:versions.realizer_formats.run_manifest}}) that lists, per warehouse, the status of its run and the files it wrote. The status is OK, REFUSED (an input the Realizer does not accept, with the reason), CRASHED (a defect, recorded by exception type only) or SKIPPED (not measured by design: the live run's collector warehouse). Its as_of_utc is the one measurement time the run used; a live run without --as-of fixes it when it starts.

ID families

Every Realizer ID is a content hash, built the same way as the Publisher's: a prefix plus the first {{fact:hash_hex_length}} uppercase hex characters of a SHA-256 over canonical JSON ({{cite:src/realizer/contracts/realization.py::content_id}}). Identical inputs give identical IDs, which is how a re-run recognises an event it already recorded and suppresses the duplicate.

The ledger

One file per RPKG, one canonical JSON object per line, appended with an fsync and never rewritten ({{cite:src/realizer/packager/ledger.py::append_if_absent}}). An entry whose id is already present is suppressed, so re-running a day changes nothing. A run holds an exclusive lock on the ledger, and a write cut short is repaired by the next lock holder before anything else. These are the example's seven entries, in ledger order:

{{table:ledger}}

REALIZATION_CREATED

Recorded first by every run: the lineage exists. Its payload copies the package's cost profile, run scope and observed change, so the history is self-describing.

APPLICATION_OBSERVED

The warehouse configuration changed to the recommended value. Effective at the epoch start of the change, not when the Realizer noticed it. It opens the application episode {{rpkg:application.active_episode_id|id}}.

VALIDATION_READY → STARTED → COMPLETED

Readiness passed, the validation window was set and the guard rules were judged. The three entries share one validation episode and the policy snapshot that judged it.

COUNTERFACTUAL_RECORDED → ECONOMIC_MEASUREMENT_RECORDED

The counterfactual's method, cost and assumptions, then the measurement that uses it: economics, attribution, realization and recognition status. The measurement points at its counterfactual id.

Two times on every entry: effective_at_utc is when the fact became true in the world, recorded_at_utc when the Realizer wrote it. A replay cut (--replay-through) projects the ledger as it stood at an earlier time. The full envelope:

The realization package

The RPKG is the ledger folded into one current view ({{cite:src/realizer/packager/snapshot.py::project_snapshot}}). Its history block records the checkpoint it was projected from: the entry count, the first and latest entry, and ledger_checkpoint_hash, a SHA-256 over the ordered entry ids ({{cite:src/realizer/packager/ledger.py::ledger_checkpoint}}). That hash, with the projector version, is what the snapshot id hashes, so a snapshot names exactly the history behind it.

{{explorer:rpkg||1|economics.annualized_realized_savings}}

Unknown material facts are null, never zero: in the example aws_cash_realized is null because no cash AWS bill was observed, while aws_economic_realized carries the modeled value.

Measurement evidence

A live or demo run first writes what it read from the system tables to state/realization/measurements/ (format {{fact:versions.realizer_formats.measurement_evidence_format}}), then projects the normalized observation from it ({{cite:src/realizer/analyzer/projector.py::project_observation}}). --from-evidence replays that file and gets the identical result offline, which is how a measurement is audited or re-run under a new Realizer version. The guide trims the 365 daily billing rows to three.

{{explorer:measurement||1|windows.post.replay}}
  • epochs: the configuration timeline; the change is the boundary between the last two.
  • windows.pre and windows.post: settled whole-day windows either side of the change, with running time, restarts and the replay rows per candidate auto-stop value (the size runtime or cluster levels for other knobs).
  • daily_cost: billed DBU and list cost per day, including restated and unpriced quantities; the financial-quality gates are computed from it. A window in which the warehouse ran but that has no billed day has an unknown billed cost (null, never zero), and the step is not measured, reason BILLING_INCOMPLETE.
  • guard: guard metrics for the previous and current epoch; assumptions: the package's thresholds and restart costs the measurement used; aws: the modeled cluster-hour price per window.
Check yourself
You re-run the Realizer on the same day with the same evidence. What changes in the ledger?

Nothing. Every entry's id is a hash of its content, and an entry whose id is already in the ledger is suppressed. The run folder gets fresh copies of the same RPKG and snapshot.

Billing for an already-measured week is restated. How does the ledger show it?

A new measurement entry with the corrected economics and a corrects_entry_id pointing at the original. The original stays. Realized-to-date uses the latest measurement for each covered day.

Why does the snapshot id include the ledger checkpoint hash?

So a snapshot names exactly the history it was projected from. Two snapshots with the same id are guaranteed to rest on the same ordered entries and the same projector version.

Where would you look to audit the example's counterfactual cost?

The COUNTERFACTUAL_RECORDED entry gives the method, the cost and its assumptions. The measurement evidence holds the replay rows and the billed days it was computed from. --from-evidence on that file reproduces it.
